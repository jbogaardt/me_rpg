# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A top-down RPG built with PixiJS v8 + Vite + TypeScript. The repo and the deployed site are fully public, so never commit secrets or private assets. Deployed as a static site to GitHub Pages.

## Direction

The game is intended to become Zelda-like: real-time action combat, item collection, and progression (leveling skills, weapons/armor, magic), told as many varied D&D-style worlds rather than one. The code is split into scenes, systems and entities (below), and the content (enemies, people, biomes, scenario nodes, quests, items, shops, loot) is data in `public/content/<campaign>/*.json`, read through `ContentManager` so it can later come from a database. There are two fixed campaigns, `campaign1` (the original world: the Vale, Lanternrest, Maren's story) and `campaign2` (Emberfall Isle, a small test campaign proving the engine runs other content), and **random campaigns** assembled from mix-and-match **packs** (`public/content/packs/`, below) with a seed. **Campaign 1 is the sandbox**: the page plays it unless the address says otherwise (`?campaign=campaign2`, `?campaign=random`, or `?seed=N` alone for a random world; `VITE_CAMPAIGN` at build time changes the default, `DEFAULT_WORLD` in `content/campaignChoice.ts`), and every new capability is built and tried there first, then made general enough for the packs. **Online, the host is the Dungeon Master** (below): hosting is running the world, not playing in it; solo play is unchanged and is where new abilities are tried. **Next** (not started): the world built on the fly from a log of the DM's story choices (an arc's steps, solved into regions from the arc's cues; dials such as weather; votes the DM can call), zone instances (one map placed more than once), and later a database of worlds and catalog (duckdb-wasm) and AI help for the DM (new arcs and NPCs through the same validated steps). Art, story and gameplay are iterated on incrementally.

## Where a feature belongs (decide this for every new feature)

Every feature lives in one of these layers; say which in its bullet below when you add or change it, and keep the line between them clean:

- **Core engine** (`src/core`, `src/net`, `src/map`, `src/entities`, the rules in `src/systems`, the map pipeline): what every world needs and no story would switch off (moving, combat, doors and zones, co-op, the inventory). It is written against registries and properties, **never against a content id**: no `itemOf('waterskin')`, no `'greenwood'` in `src/` (ask an item property such as `waters`, a role such as `QUEST_GIVER`, or a biome's own data instead). Known leftovers from campaign 1, to clear when touched: the trainer `TRAINER = 'orin'`, the skills' training grounds (`SKILLS[].zone`) and the `'town'` fallbacks in `guide.ts`/`QuestLog.ts`.
- **Capability** (`CAPABILITIES` in `src/systems/capabilities.ts`): an engine system some stories want and others do not (the map, hunger, combos, weather...). It is gated with `enabled(id, zone)` at its one choke point, tuned with `setting`, switched per campaign, arc, biome or region, and the content checks refuse content that asks for it where it is off (`checkAgainstCapabilities`). When a new system is something a story could do without, make it a capability in the same change (see Capabilities below).
- **Content** (a campaign's five files, validated by `src/content/schema.ts`): what a world holds (who, where, what story, which goods). A new *kind* of thing is a schema field with its reader and cross-checks (every id it names must exist), an install step in `ContentManager.install` into a registry the engine reads, and a check in `tools/content/campaigns.test.ts` or the map check where a rule spans campaigns.
- **Packs** (`public/content/packs/`, `src/content/packs.ts`): the same content in mix-and-match form for random worlds; a new content kind gets a pack section (merged with the clash check, validated by `checkPacks`) once it is general enough. Campaign 1 gets a feature first; the packs get it when it no longer assumes campaign 1's world.
- **Co-op** is not a layer but a question for every layer (see Conventions): what the host owns and what a guest is sent.

## Commands

- `npm run dev` — Vite dev server with HMR (also exposes `window.__game` for playtest scripts, dev only)
- `npm run build` — typecheck, `map -- check`, `sprites -- check`, then production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run verify` — everything CI runs except the build and browser tests: lint, format check, typecheck, unit tests, map check, sprite check. **Run it before committing** when it is quick; see Working procedure for what must not block a push.
- `npm run lint` / `npm run format` / `npm run format:check` — ESLint (type-aware) and Prettier (`.ts`/`.json`/`.yml`; CSS, HTML and Markdown are hand-formatted)
- `npm run test` — Vitest unit tests (`src/**/*.test.ts`, `tools/**/*.test.ts`)
- `npm run test:e2e` — Playwright smoke tests against the production build (set `PW_CHROMIUM` to a local Chromium, e.g. `/opt/pw-browsers/chromium-*/chrome-linux/chrome` in cloud sessions)
- `npm run typecheck` — typecheck only (game, `tools/`, `e2e/`, `relay/`)
- `npm run relay` — the matchmaking relay in memory on `http://localhost:8787` (use with `VITE_RELAY_URL=http://localhost:8787 npm run dev` to try online play locally)
- `npm run map -- build|check|render|layout …` — zone specs → map JSON + previews + checks; `layout <biome>` prints a biome's walls, gaps and open ground (see Map pipeline)
- `npm run sprites -- build|check|preview …` — LPC part catalog → packed layer sheets (see Characters). `build` needs a clone of the LPC generator (`LPC_DIR`); `check` (run by `verify` and `build`) does not

CI (`.github/workflows/ci.yml`) runs `verify`, `build` and the e2e tests on every pull request; the deploy workflow runs `verify` before publishing.

## PixiJS skills

Vendored in `.claude/skills/` (`.agents/` is a gitignored duplicate). **Before changing anything in `src/` that touches PixiJS, load the `pixijs` skill** and follow the sub-skill it routes to (application, assets, scene-*, ticker, performance, math). Only the sub-skills this game uses are vendored; for anything else the router falls back to the live docs (`https://pixijs.download/release/docs/llms.txt`), or re-add a skill with `npx skills add pixijs/pixijs-skills`. Project conventions that follow them: `TextureStyle.defaultOptions.scaleMode = 'nearest'` and `resolution: devicePixelRatio` + `autoDensity` are set once in `main.ts` (don't set scale modes per texture); dynamic in-world text uses `BitmapText` with the pre-installed `FloatText` font, not `Text`.

Other project skills: `build-zone` (any map change), `add-mob-kind` (new enemy), `add-sprite-part` (new hair/armor/weapon/monster part), `add-particle-effect` (new/retuned particle effect), `playtest` (run/screenshot the game in a browser).

## Architecture

Pixi-free logic (rules, collision, camera maths, map format) is kept separate from Pixi code so it is unit-tested without a browser; keep it that way.

- `src/main.ts` boots: creates the PixiJS `Application` (async `app.init`, wrapped in a `void` IIFE — avoid top-level await), registers the manifest, loads the content (`ContentManager.load(staticContent)`, then `install()`), loads assets and the start node's zone behind the loading overlay, creates the shared DOM UI (`Hud`, `Menu`, `Dialog`, touch controls) and starts a `SceneManager` with an `OverworldScene`.
- **Content (data-driven: `public/content/<campaign>/` and `src/content/`)** — what the world holds is data, not engine code. A **campaign** is a folder of five JSON files (validated on load, `src/content/schema.ts`, Pixi-free and tested; a bad file stops the boot with every problem listed, `ContentError`): **`entities.json`** (every mob and NPC by id: `type` `mob`/`npc`, `name`, `notes` for designers, `sprite` = a paper-doll `Outfit`, `scale`; mobs have `stats` {hp, attack, defense, speed px/s, sight px, xp, gold} and `behavior` {windup, recover, stagger, `shot`, `ray`; colours `"#rrggbb"`}; an NPC placed by a scenario says its `lines`), **`biomes.json`** (by `biome_type`: its on-screen `name` (`ZONE_NAMES`), `tint` (the iris rim, `ZONE_TINTS`), `links` (the zones walkable from it in preference order: the guide's routes, `nextZone`; checked against the maps' doors), the `map` it is drawn from, `climate` (null in a room), `music` (unused: there is no audio yet), `tilesets` (written by `npm run map -- build` from the map; loaded alongside the map JSON) and `generation.roam`: enemies spread over the biome's open ground when the zone loads, deterministic by `seed`, `content/populate.ts` `roam`) **`quests.json`** (the story: `giver` (whose chain it is), `givers` (name, `look` = an npc entity, tag, zone), `sites` (gather spots: name, shape mushroom/stone/sand, colours, notes), `chapters`, `quests` (the chain in story order, the `Quest` shape of `systems/quests.ts`; objectives `kill`/`gather`/`bring`, rewards naming item ids of its items.json) and `epilogue`), **`items.json`** (its goods, below) and **`scenarios.json`** (a graph of nodes: `node_id`, `biome_type`, optional arrival `spawn`, `entities` [{ entity, x, y } in the map's cells] and `choices` [{ text, next, requires?: { stat: level/attack/defense/magic, min } or { skill } }]; `start` is where the game begins). `ContentManager` (`src/content/ContentManager.ts`) fetches them from a `ContentSource` (one method, `fetch(file)`; the static files are `assets.ts` `staticContent`, `UrlContentSource` reads any URL serving the same JSON, so a database is a new source and one line in `main.ts`), caches them and answers `getScenario`, `getBiomeInfo`, `getEntityBaseStats`, `mobKind`, `populate`; `install()` fills the registries the rules read by id (`MOB_KINDS` in `systems/combat.ts`, `NPC_LOOKS` in `systems/looks.ts`, `ZONE_NAMES`/`ZONE_LINKS`/`ZONE_TINTS` in `systems/places.ts`, `QUESTS`/`CHAPTERS`/`GIVERS`/`SITE_KINDS`/`QUEST_GIVER`/`EPILOGUE` in `systems/quests.ts`, `ITEMS`/start gear in `systems/items.ts` (`setItems`), `SHOPS` in `systems/shops.ts`, `CHEST_LOOTS` in `systems/chests.ts`; all empty until then). **Goods (`items.json`, `parseItems`)**: `start` (the gear a new hero wears, an item id per slot, the weapon always; `newHero` reads `startGear()`), `items` (id → an `Item`: `name`, `value`, `slot` or `use`, `attack`/`defense`, the buffs, `rare`, `waters` (crops are watered with it, `waterWith`), `capacity` (bags), `ranged` {speed, range px, cooldown} (bows), `focus` {kind wand/tome, power, cooldown, `combos` [{keys, spell (a `SPELL_IDS` effect: what a spell *does* is engine code in `Casting.ts`, which weapon carries it and for how much is content), cost, power, count}]}, `look` (doll parts)), `shops` (id → name, tag, `keeper` (an npc entity), `greeting`, `stock` (item ids; never a `rare` one), `buys`: gear slots and `TRADE_KINDS` (`blade`, `bow`, `caster`, `supply`), `shopBuys`) and `loots` (chest contents: `{ item }`, `{ hp, mp? }`, `{ xp }` or `{ gold }`; the map's `z.chest` names one). The checks refuse an unknown field, a worn item that is also used, a bow/wand that is not a weapon, a combo with a repeated tap, an unknown spell or one hidden inside another combo or a skill's, an item named anywhere (start, stock, loot, quest) that the file lacks; `npm run map -- check` fails a chest loot or crop produce the map's campaign lacks, and `tools/content/campaigns.test.ts` holds every campaign's items to real parts in their slots and no spell or combo on two weapons. **Item codes** (the wire, `itemCode`) are an item's place in its campaign's list, so a campaign's file is append-only once players are on it; both co-op players play the same content, so they agree (no protocol change per campaign). Campaign 1's file holds the original 55 items and five shops, campaign 2 a short list of its own (no shops), the packs' goods are the `outfitters` pack. The static source is `staticContent(campaign)` (`content/<campaign>/<file>.json`; `assetVersions` hashes subfolders too). **Which world** (`content/campaignChoice.ts`, tested): `?campaign=<folder>` or `random` (default `DEFAULT_WORLD`, campaign 1, unless `VITE_CAMPAIGN` names another), `?seed=N` (alone, it means a random one) (a fresh seed is written into the address, so a reload or a shared link is the same world). **Packs and random campaigns** (`src/content/packs.ts`, Pixi-free, tested; `packContent(seed)` in `assets.ts` → `AssembledSource`): a pack (`public/content/packs/<id>.json`, listed in `packs/index.json`) holds any of `entities` (as in entities.json; a mob also has `tags`, its roles `common`/`hunter`/`ranged`/`brute`/`boss` and themes `fire`/`frost`/`swamp`/`undead`/`beast`, a `level` band and a `plural`), `keepers` (who gives a story: an npc entity, name, tag, the hub `homes` they live in), `regions` (a biome without links/ports/generation, a `level` band, `themes`, `hub` (has a `keeper` spot, can start a story), `terminal` (a dead end: one port, never in a story), its map's `ports` with the edge each is on (`{ "north": "north" }`, checked against the map; at most one per edge), the `foes` roles that live there, `roam` and `encounters` by role, its `sites`), **`pairings`** (how two regions meet: **two regions are only ever joined where a pairing names them**; its `tags` say what kind of meeting it is (`thaw`, `frost-creep`, `restless-dead`, `fire`...), `ports` optionally fix the doorways, and `lore` holds lines written for that pair, one line or one per region it is seen from: `way`, `sign`) and `arcs` (a story whose quests name roles, not ids: `"@r2.boss"` the mob picked for region 2's boss, `"@r1"` region 1's map, `"@r1.site"` its site kind; in text `{r1}`, `{r1.common}`/`.plural`/`.lower`, `{r1.site}`, `{keeper}`, and `{r1~r2.sign}` a lore line of the pairing the story crosses from r1 to r2, seen from r1; constraints: `slots` per region (`regions`, `themes`, extra `foes` tags such as a fire boss), `crossings` (`"r1~r2": { tags }` the pairing there must carry), `keepers`; a quest or chapter's `variants: [{ when: { "r1~r2": "<pairing id or tag>" | "r1": "<region>" or "theme:x" | "keeper": id }, ...fields }]` replace its fields for that meeting of biomes, which is how a story tells a detailed cross-biome quest). `assemble(seed, packs)` refuses packs `checkPacks` finds wrong (an id two packs both define (`mergePacks` records the clash; a pack never silently overrides another's), two regions drawing one map or owning one site kind, an arc switching an unknown capability, a pairing of an unknown region or port, a region nothing pairs with, a keeper's home that is not a hub, an arc quoting a pairing between regions that are not neighbours in its story), then picks an arc and the regions it needs (`storyFor`, built to scale to thousands of regions: the regions each slot could take are worked out once (an arc some slot of which nothing fits is dropped at once), the search walks only pairing partners (`cat.pairs`, an index by region; `pairingsBetween`, `partnersOf`), and it gives an arc up after `STORY_BUDGET` placements; `tools/content/packs.test.ts` assembles a made-up catalog of 3000 regions in well under 2 s: r1 a hub some allowed keeper calls home, the rest rising in level, each meeting its slot and able to fill the roles the arc names (`arcNeeds`), each step crossing a pairing that has the lore keys the text quotes and the tags the arc asks (`crossingNeeds`)), **lays the world out on a grid** (`Grid`: r1 at [0, 0], north is -y; a region goes in the cell its host's port leads to, the port it arrives by on the facing edge (`OPPOSITE`, `STEP`), so leaving north arrives in the south and **north, east, south and west through any doors comes home**; a cell is taken only if every region already beside it is paired with the newcomer, so neighbours always belong together), adds up to `MAX_SIDE_REGIONS` (3) side regions (only partners of a region already in, through a pairing, in a free cell; so the world's size never grows with the catalog), joins regions that ended up side by side where both have a facing port, then **bolts a dead end onto every open port one suits** (`terminal` regions, each once: Ember Cove, Frost Grotto, Bog Hollow, Old Shrine, built by `tools/map/deadEnd.ts`, a guard and a chest at the far end); a port still left open is sealed (below), picks a keeper and a mob per role (`candidates`: the role's tag (and the slot's extra tags), the band, and strictly one of the region's themes, so no fire brute guards the snow; a different mob per role) and writes ordinary campaign files, which `parseContent` validates like any others. Packs: `outfitters` (the goods every random campaign carries: `items`, `loots` and `start`, as in items.json; a pack may hold `items`, `shops` (their keepers come along) and `loots`, merged pack after pack with the same clash check, one pack says `start` and an arc may override it (`ArcDef.start`, a wizard's tale with a wand)), `emberfall` (campaign 2's mobs, Ysolde (at home on the coast), the coast (hub) and the caldera, their pairing `ash_trail`, the `ember_trail` arc: a fire region and a fire boss), `wilds` (goblins, wolfkin, shades, skeletons, zombies, the Barrow Lord, the Rimebound, the Fen Yeti, Keeper Ilsabet, the Mirewood (hub), Frostfen and Barrow, their pairings, the `lost_lanterns` arc: through a frost or swamp region to an undead one, over a `restless-dead` crossing) and `borderlands` (no regions of its own: the pairings across the other two packs, and `long_thaw`, a hub against a frost region whose quests change with the crossing: `thaw` from the coast, `frost-creep` from the Mirewood). Packs can be bridges: a pairing may name regions of other packs. Add a region: a `defineZone` map with `z.port`s (and a `z.giver('keeper', ...)` spot for a hub, `z.site`s for gather arcs), then its entry in a pack and a pairing (with `way` and `sign` lore) to each region it may sit beside; `npm run map -- build` writes its tilesets into the pack. **Ports** (`src/content/ports.ts`, tested): `z.port(name, col, row, w, arriveCol, arriveRow, h, seal)` marks a doorway whose far side the content decides (`MapData.ports`; left out of the file when a map has none): `w` x `h` cells (an east or west port is a column, `h` 3; doors and ports may span rows, `DoorSpawn.h`, `onDoor`), on the edge it is nearest (`side`, `portSide`), with a `seal`, the props (a rockfall, a thicket) that close it when nothing binds it (the map check fails a port without one); a biome's `ports` in biomes.json binds each to another map's port (both ways, `parseContent` checks; `npm run map -- check` fails one that does not join opposite edges), and `Zones.add` wires them into ordinary doors (`ContentManager.wire` → `wireDoors`; the arrival is the far port's `arrive`, `doorArrival`), blocking a port nothing binds and drawing its seal, so no open way ever leads nowhere. Campaign 2's coast and caldera are joined that way, so the same maps serve campaign 2 and the packs; the open-air world of campaign 1 has none. **Tests and tools**: `tools/content/disk.ts` reads a campaign from disk; the Vitest setup (`tools/content/setup.ts`) installs **campaign 1** (`DEFAULT_CAMPAIGN`), so every existing rule test runs on campaign 1, and `tools/content/campaigns.test.ts` holds every campaign's entities to the same rules (real parts, fair enemies). The map tools check each map with the campaign whose biomes draw from it installed (`withCampaignOf`; a pack region's map with the packs' catalog, `PACKS` = every region at once with no story, `catalogCampaign`), and `npm run map -- check` checks every campaign's content, the packs' catalog and the random campaigns of seeds 1-40 (`checkCampaigns`; a map no campaign or pack uses fails); `tools/content/packs.test.ts` assembles 150 seeds and holds each to the game's own checks, a story that starts in a hub, rises in level and can be walked port to port, every role and name filled in, every join a pairing, the arc's slots, crossings and keepers honoured, the grid consistent (every door to the next cell its way and the facing edge; a random walk through doors always stands where the layout says), every dead end used, and every port left open sealed. The browser tests build campaign 1 (`playwright.config.ts`, `E2E_CAMPAIGN` overrides). Maps stay in `maps/` and `public/maps/` for every campaign (campaign 2's are `emberfall_coast`/`emberfall_caldera`, standalone `defineZone` open-air zones joined by an iris door); give a new campaign's zones a prefix so names never clash. **Who stands in a zone** is the content's, never the map's: `Zones.add` asks `ContentManager.populate(zone, map, node)`, which gives the zone's scenario node's placements (mobs first, then the biome's roamers; folk apart) in a fixed order, and `ZoneState.populate` builds them (and replaces them, destroying the old ones, when another node is loaded over the zone). A zone shows the node named after its biome unless a scenario was loaded over it (`Zones.assign`/`nodeOf`). **`loadScenario(nodeId)`** (`OverworldScene.loadScenario` → `scenes/overworld/Scenario.ts`): loads the node's biome's zone, takes the local player there through the iris (the old view is cleared away) to the node's `spawn` or the map's, puts the node's entities in, and shows its choices in `hud/Choices.ts` (`#choices`, a column of buttons at the right; a choice the hero does not meet is disabled with "Needs Level 4"; picking one loads `next`). Campaign 1's nodes are one per zone (named after it, no choices) plus a sample `greenwood_ambush` (dev: `__game.overworld.loadScenario('greenwood_ambush')`); campaign 2 (`?campaign=campaign2`) starts in `landing`, whose choices lead on ("Make camp" → `cinder_coast`, "Climb straight to the caldera" needs level 4). **Checks**: `npm run map -- check` (`tools/content/check.ts`) fails a biome whose map is missing, whose tilesets or climate differ from its map, a map with no biome, a port binding naming a port a map does not have, `links` that differ from the (wired) doors, a placement or spawn off open ground of its own biome (blocked, a door, the neighbour's margin), a gather quest whose zone has fewer sites than it asks for and a kill quest whose mob lives nowhere it says; it warns when a roam rule cannot place them all. **Co-op**: both players must play the same world: the hello's `build` carries it after a `#` (`setContentTag` in `net/session.ts`, from `CampaignChoice.tag`, e.g. `random:42`), and a friend in another world moves to the host's world by itself (see Co-op: the lobby and joining); the join link keeps the address's `?campaign`/`?seed` (`hud/Multiplayer.ts`). **Scenarios: solo only for now.** The host does not send a node: online, `Scenario.update` puts every zone back to its biome's own node and hides the choices, and `loadScenario` refuses. Because populations are deterministic from the content and the map, a guest builds the same mobs in the same order as the host (snapshots refer to mobs by index) with nothing on the wire; when the host comes to dictate the node, it must send `node_id` per zone and the guest `Zones.assign` it.
- **A world from a log (`src/content/world.ts`, Pixi-free, tested in `tools/content/world.test.ts`; content)** — a world is a seed, the packs, and an append-only **log** of fully resolved entries (`LogEntry`): `begin` (the arc, its keeper, the hub r1 and its foes), `step` (the story's next region: the pairing crossed, the ports, the mob for each foe role), `side` (a side region or a dead end beside a region already in) and `join` (a door between neighbours). `World.apply` checks each entry against the packs' rules (the arc's slot, rising level, a pairing serving that step, a free port leading to a grid cell whose neighbours all pair with it, foes that fit their role) and refuses it without changing anything (`WorldError`); `replay(log)` rebuilds a world with no random numbers, so every co-op player and every later solver agrees. `files()` writes ordinary campaign files for the world as it stands: an unfinished story carries its quests in order up to the first that names a region not yet placed (`told()`, by the regions a quest, its variants and its chapter's intro reach), and the epilogue only once complete. **`assemble` (random campaigns) is an automatic Dungeon Master on top of it**: it finds a whole story (`storyFor`), writes its steps, side regions, joins and dead ends as entries, and returns the log with the files (`Assembly.log`). **A live world** is written during play: `open(arc?)` begins it and places as many steps as its first chapter needs; then `options()` offers the next step as **story cues** (`StoryOption`: a kind of land and of crossing, "Into frost lands, over a thaw crossing"; never a map), only those after which the rest of the arc can still be told (`storyFor` resumed from the story so far, `nextPlacements`), and `choose(cue)` resolves one (seeded by the world's seed and the step, so it is the same on every page) for `apply`. The maps are the solver's: an "endless desert" is a chain of different desert regions, so more regions per theme in the packs is what makes longer stories possible. **In play** (`?campaign=live&seed=N`, optionally `&arc=<id>`; `campaignChoice.ts` `LIVE`, tag `live:N[:arc]`): `LiveSource` (`assets.ts` `liveContent`) opens the World and serves its files, and the boot preloads every pack entity's look (`worldLooks`, `loadSprites(_, extra)`) since the story may bring any of them. `scenes/overworld/Story.ts` grows it: whoever may choose (`canChoose`: solo, the player as their own DM, which is how a story is tried out; online only the host, the DM) picks a cue on the **story card** (`hud/DmCard.ts`, offered by `scenes/overworld/DmPrompts.ts` when the party has finished what was told, or on demand from the DM bar's Story button: the roads as buttons; textContent only), and each new entry is applied (`World.apply`), the content reloaded (`ContentManager.reload`: everything but the goods, which a live world never changes and whose item objects heroes hold) and **the ports it binds open in zones already loaded** (`Zones.rewire`: `openPort` in `content/ports.ts` gives the door, the cells its seal blocked and the seal's objects, which fade, `MapView.setObjectAlpha`; nothing else in the zone changes), with "The way opens" over the doorway and the new land's name in the `AreaBanner` on every page. **Co-op**: the host sends its friends the log a few entries at a time, round and round, newest first when one is added (`WorldMsg`, `WORLD_CHUNK` 3, every 0.4 s; protocol v30), and a friend applies the entries that follow on from its own (it opened the same world from the same address, so its opening matches; one that does not fit marks it astray). Not yet: quests run out at the end of what is placed until the DM chooses the next step. **With today's packs every step offers one road** (too few regions and pairings to branch): the choice is real in the engine and grows with the packs' regions per theme and pairings.
- **The Dungeon Master's controls (core engine, co-op): a bar that is always there and cards at the right moment, never an admin panel.** The DM has no menu tabs of their own but Party (`hud/Party.ts`, each player's level, HP, area and a **Go** button). - **Wands, tomes and combos** — a wizard's shop (`shop_wizard`, door in the town, in the east beyond the ranger and clear of the north road) sells wands and tomes (`ITEMS`: `apprenticeWand`, `stormcallerWand`, `noviceTome`, `arcaneGrimoire`; `Item.focus`, a `Focus` from `systems/spells.ts`, Pixi-free and tested). - **`src/systems/`** — `combat.ts`: stats, gear, the `MobKind` type and its `MOB_KINDS` registry (filled from `entities.json`, see Content) and the damage/XP/level-up rules (`newHero`, `rollDamage`, `gainXp`). **Balance** (`systems/balance.test.ts` guards it): each `MobKind` is tuned for a band of hero levels (a fresh hero with the starting sword cannot take the deep kinds: one blow takes over 80% of their HP and the kind needs over 60 swings) and the biomes hand them out by band (greenwood 1-3, eastwood and the coast 3-5, barrows and desert 4-6, frostlands 5-8, the Mirewater 6-8, the jungle 7-9, the marsh 8-10; the deeper kinds are `hexer`, `bogGhoul`, `warg`, `tuskGuard`, `frostWarden`). Bows deal about 75% of a same-priced sword's damage per second, a wand's plain bolt about 65% and a tome's about 40%; a combo is a burst for mana (about 1.4-2x a plain bolt per target), not a better sword, and a ward is up under a third of the time it can be recast. Retune a weapon or kind against that test. Biomes spread extra wanderers with `generation.roam` in `biomes.json` (kinds, count, seed, apart, `avoid` circles such as round the spawn), on top of the packs the scenario node places. Levelling is superlinear: `xpToNext(level) = round(20 * level^1.5)` and `levelGains(level)` (stat gains per level-up) steps up every 4 levels; mob XP is fixed per `MobKind`, so a new tougher kind is how higher levels stay meaningful. `particles.ts` (Pixi-free `Emitter` simulation with fixed pools) and `particleEffects.ts` (the effects, pure data; add one with the `add-particle-effect` skill). `collision.ts`: `Collision` (cell collision from the map plus body-vs-body blocking: characters block each other but can always move apart; per-axis `slide`).
- **`src/entities/`** — `Character.ts` renders the hero/NPCs/mobs from a composed *doll sheet* (below): looping idle/walk follow `animate(dt, moving)`, one-shot `play('slash'|'cast'|'hurt', ms?)` takes over until done, `setSheet()` swaps the look when gear changes. Its container origin is the *feet*, so collision and y-sorting (`zIndex = y`) use it directly. `Mob.ts`: enemy AI state machine (idle/wander → chase the nearest hero → telegraphed windup → strike → recover; stagger on hit; fade and respawn at home), driven through the `MobWorld` interface the scene passes in (`strike` for melee, `shoot` for projectiles); pacing is per kind (`windup`/`recover`/`stagger` via `mobTimings`, so tough kinds shrug off stun and quick ones swing fast); **a hero cannot juggle a mob**: after one stagger it shrugs off further stagger for `POISE` (0.9 s; the damage still lands, it is only shoved) and past half its windup a blow cannot be interrupted, so it always gets to swing back, and **a melee blow cannot be dodged by stepping back and forth** (core engine, `Mob.ts`): it starts winding up from `REACH` (32 px, more than the sword's own reach, so a hero close enough to poke is close enough to be swung at), each windup is ±20% of the kind's (`WINDUP_SPREAD`, so the rhythm can't be learned), it turns to follow the hero until the windup is committed and then locks its aim, and the blow is a real lunge along that aim (`lungeOf`: quick kinds leap up to 34 px, slow ones 14; the body moves, so a guest sees it from the snapshots with nothing new on the wire) that hits whoever is in the circle in front of it (`HIT_AHEAD`/`HIT_RADIUS`); a small step back is caught, a sidestep once the aim is locked or an early full retreat dodges, and a blow that misses leaves it busy only `WHIFF_RECOVER` (40%) of its recover before it presses in. A mob that loses the hero mends (`MEND`, a quarter of its HP a second while idle or wandering), so a hero can't chip at it, run off to heal and come back, and a kind with a `ray` (the desert **Mummy**) is a caster with a melee fallback: within `REACH` it swings (`slash`); from `ray.range` (4.5 cells) it thrusts its sceptre (windup), then enters the `channel` state: it faces left or right (the sheet has no up/down attack art) and holds the sceptre-thrust frame (`Character.hold`/`release`, `RAY_POSE` in `Mob.ts`, which also records where the sceptre head is) while a pink beam runs from that head to the hero that burns every `ray.tick` s for `ray.power` x its attack (`MobWorld.ray` → `Simulation.mobRay`: a damage-over-time `harm(..., burn)`: no knockback, stun or invulnerability, spared while `safe`). The beam ends when `ray.duration` runs out, the hero gets past 1.4x the range, a wall comes between them, or **any hit on the mummy** (`Mob.hit`, however poised: it is staggered); then `ray.rest` s of melee only (`mobAttack(kind, dist, rayReady)`). **Co-op**: `channel` is a `MOB_STATES` entry (protocol v25) and every client draws the beam itself from that state to the nearest hero (`Mob.drawBeam`, a guest uses `Mob.setRemote(view, heroes)`); the host alone burns. **Giants**: `MobKind.scale` (the Abominable Snowman is 2) draws a kind bigger (`Character.setScale`, `Character.size`) and the rules follow it: `Body.size` widens its collision foot box and its body-vs-body blocking (`systems/collision.ts`), its melee reach and strike distance grow with it (`mobAttack`), the hero's sword and arrows hit a bigger circle, and its health bar and floating numbers ride higher. A kind with a `shot` is a ranged attacker (stops at range, backs off when crowded, telegraphs with the cast pose, then fires a slow `foeBolt` the scene flies and tests against the players); on a co-op guest the same class is only a view of the host's state (`setRemote` also plays its windup and hurt poses). `effects.ts`: transient world visuals (slash arc, bolt, floating `BitmapText` numbers) owned by an `Effects` list. `ParticleEffect.ts`: draws a data-defined particle effect (`ParticleContainer`, one per emitter) as an `Effect`; spawn with `particleEffect('name', x, y, { dir })`. Character theme: a boy stranded outside time.
- **Characters (paper-doll)** — `src/sprites/doll.ts` (Pixi-free) defines the doll sheet and outfits: every layer is packed by `tools/sprites` onto one 832x1600 layout (64px frames for walk/idle/cast/hurt/shoot, 128px frames for the weapon swing; rows up/left/down/right) so layers stack frame-for-frame. The trade ends if players drift past `TRADE_KEEP` (5 cells), leave, or either cancels (Esc / the ✕ cancels an open trade). Only pack items can be offered (not worn gear). On the wire (`tr` guest→host, `trade` host→guest, `protocol.ts`) commands are numbered and the guest repeats every unacknowledged one until the host's `ack` covers it (the host takes only the next number), so the lossy channel can't drop a click; the host sends each friend their view/note when it changes and once a second; the gold/pack result then arrives through the normal `pack` message. `TradeUi.sync` draws from a `TradeView` every frame; `OverworldScene` (`syncTrade`, `tradeCommand`, `handleTradeSteps`, `sendTrade`) joins it to the book (host: direct; guest: queue + host view). - **Food and water** — `systems/needs.ts` (Pixi-free, tested): `Hero.needs` = `{ food, water }` (0..100, start full). They drain with time (food lasts about 20 minutes, water 14; `drainNeeds`, run in `Simulation.updatePlayer`, so solo/host only) and are refilled by supplies whose `use` has `food`/`water` (`bread`, `roastMeat`, `apple`, `waterskin`, sold by the apothecary, eaten from the Inventory like potions; `useFromPack` refuses when nothing would change). `needsRegen` scales the natural HP/MP regeneration by the worse meter (well fed 1.25x, hungry 0.5x, empty 0; gear that mends is unaffected) and only when both meters are empty does it cost health (`starveRate`: 3% of max HP per second, in `Simulation.updatePlayer`; it leaves 1 HP, never kills). `Hud` shows Food and Water bars in a second row under HP/MP (`#hud-needs`). **Drinking from a pond**: standing at the edge of clear pond water (surface `water`; the sea, swamp `bog` and ice do not count) while not fully watered shows a **Drink** button by the water (none by an empty pond) (`drinkableNear`, `DRINK_REACH`, `thirsty`; drawn by `hud/HarvestButtons.ts` with `DRINK_KEY`; it reads **Stop** while drinking). **The action key (A on touch, Space or a left click) drinks too**: in `OverworldScene.act`, after chests, crops and sites and before picking up or swinging, `Simulation.pondAction` stops a player who is drinking or starts one for whom `canDrink` (thirsty, beside a pond that is not empty), so by a pond A drinks instead of attacking while thirsty, **but only while no enemy is near** (`foeNear`: a live mob within `FOE_NEAR`, 6 cells): in a fight A always attacks and stops a drink in progress (the Drink button still drinks); a guest's A press reaches the host's `act` like any other, and the guest flips its own `guestDrinking` to keep the button label right. Drinking is steady, not in sips: `Simulation.startDrinking` turns the hero to the pond and sets `Player.drinking`, then each tick (`drinkTick`) `POND_FLOW` (8) water a second flows from the pond into them (`sipWater`) until they are full, walk off, press Stop or the pond is dry ("The pond is dry"); the total floats when they stop. **Ponds drain**: each pond (`pondId`, a flood fill of joined water cells) holds `WATER_PER_CELL` (1.5) water per cell (`pondCapacity`) and `PondLevels` (one per `ZoneState` as `ponds`) keeps how far each is drained (0 full .. 1 dry). **Only rain fills a pond again**: `Simulation.weather` calls `ponds.rain(rainFill(precip, intensity), dt)`; rain fills a dry pond in `RAIN_FILL_TIME` (120 s) at full intensity, a storm twice as fast, snow, sand, ash and clear skies not at all, and only in zones someone is in (where weather runs). A pond drunk dry is `refilling` (`PondLevels.refilling`) until full again and fills **from the middle out**: `PondBeds.drawRefill` cuts the water back into the bed ring by ring from the middle while the outer rings stay dry, and lily pads return as the water reaches them; a pond only part drunk goes back the way it went. Levels (and the refilling flag) are kept in `ZoneMemory.ponds` while a zone is unloaded. **Drawn in layers**: `pondLayers` splits a pond into rings from the shore in, and `drainedLayers` says how many are gone and how far the next has faded; `entities/PondBeds.ts` (a `Graphics` in the zone's `world.layer` at ground level, blurred soft, cached as a texture and redrawn only when a level visibly changes) washes each gone layer in the ponds' own blue a shade lighter (shallow water, kept off the sandy bank) and fades the one going now to it, so the deep blue shrinks ring by ring; only as the last layer goes does the earthen bed fade in, so a pond is brown only when empty. The bed follows the shore: `map/outline.ts` (`cellsOutline`, Pixi-free, tested) traces a set of cells the way the corner-painted terrain draws it (marching squares over the cell corners, the edge `BED_REACH` of the way into the bank cells, rounded by Chaikin's `roundOff`), so it covers the water at the edges and corners; its edge is the banks' tan, so the ground runs on into it, and each ring further in is the same smooth shape a size smaller and a shade darker. Props standing in a pond's water (lily pads) fade out with the last of it and come back as rain fills it (`MapView.setObjectAlpha`: a fade per map object, kept while its chunk is freed and rebuilt). **Co-op**: the host owns the meters and sends them whole in `PackMsg.needs` (protocol v20); a guest only displays them. Its Drink/Stop button sends `DoMsg` op `drink` (item 1 start, 0 stop; protocol v27), which the host checks against the pond beside that friend (`PackSync.tradeFor`); a guest's own idea of whether it is drinking (`guestDrinking`) ends when it walks or is full, as the host's does. The host alone drains and rains on ponds and sends each zone's drained ponds in the snapshot (`SnapMsg.ponds`: flat id, thousandths drained, negative while refilling; absent = all full; `pondsWire`/`pondsFromWire`); the guest only draws them. - **Zones and doors (several maps, one world)** — a *zone* is one `MapData`: the ten open-air biomes of the world (`greenwood`, the start, `town`, `eastwood`, `desert`, `beach`, `undead`, `jungle`, `wetlands`, `marsh`, `frostlands`; see Map pipeline → World) and a room per shop (`shop_smithy`, `shop_armory`, `shop_apothecary`, `shop_ranger`, `shop_wizard`). `MapData.doors` (`z.door(col, row, w, toZone, toCol, toRow)`) are cells that take a player to another zone; `MapData.indoor` (`z.indoor()`) rooms get no weather, ambient or overview map. Pixi-free geometry in `map/doors.ts` (`doorAt`, `doorsNear`, `arrivalFacing`, tested). `scenes/ZoneState.ts` bundles everything per loaded zone (`MapView`, `Collision`, `Camera`, `Effects`, mobs, chests, shopkeepers, ground items, `heroBodies`); `OverworldScene` keeps `zones` (by name) and each `Player` has a `zone`. **The scene works in one zone at a time through `this.zone`**: outside the per-zone loops it is the local player's zone (`this.view`, the only one drawn, swapped onto `stage` by `showZone`, under a `ZoneTransition`), and `inZone(z, fn)` points it at another zone for a moment so one set of rules (`mobs`, `chests`, `players()`, `bodies()`...) serves all of them; `players()` is the players in the current zone, `everyone()` all of them. **Efficiency**: only zones with a player in them are simulated (`occupiedZones`), so a shop nobody is in, or a zone everyone has left, costs nothing; zones load on demand (`ensureZone` via `assets.loadZone`) and `prefetchDoors` starts loading the zone behind any door within 5 cells of a player (host: of every player; guest: of the local one) so stepping through is instant, and a door whose zone is not ready yet simply waits a frame. **Memory stays bounded**: `Zones.retire` unloads a zone nobody has been in or near a door into for `RETIRE_AFTER` (20 s) (never the start zone, which a defeat wakes you in): `ZoneState.dispose` frees its map, mobs and characters (their sheets go back to the wardrobe), `assets.unloadZone` frees its map and every tileset no other loaded zone uses (tilesets are reference-counted), and what must last is kept in `Arena.memory` (`ZoneMemory`: opened chests and the items on the ground, with their ages; `Ground.stash`/`restore` include it) and given back by `Zones.add` when it loads again (its mobs start afresh). A guest counts only itself. A zone that is loaded but not shown has its map sprites freed (`MapView.release`). **Travel** (`travel`): host/solo move the player (`doorAt` each frame, not while reading a dialog/shop), set their zone, place them at the door's `to` cell facing away from the door, give `ARRIVE_GRACE` immunity (`Player.grace`, 1.8 s, longer than the transition because the world runs behind it; silent, unlike the blinking `invuln` after a hit, and `Player.safe` is either) and play a **door transition** for the local player (`beginTrip`): **walking from one open-air zone into the next is not a transition at all** (`Zones.seam`: both zones open-air and the door names its direction, i.e. a gap in the border). The zones are laid out like one map: `neighbourLinks` (`map/doors.ts`, Pixi-free) gives, for each gap, where the other zone's coordinates sit against this one (`to - door - direction * (1 + ARRIVE_CELLS)` cells; `tools/map/links.test.ts` checks it against the built maps), and while a player is in a zone the open-air zones joined to it are drawn beside it, nested in the player's own world at that offset (`Zones.syncNeighbours`/`update`: they share its camera, `MapView.update` builds their own view rect) and layered between its ground and its objects, so every zone's ground is under everyone's trees (a crown never sinks into the next zone's grass); a zone to the south (`Link.dir` `down`) goes over the player's objects, any other under, each drawing only its own cells (`MapView` skips the neighbour margin, surface `beyond`, which the neighbour draws), so the two join without a seam and you see the next biome's land, props, NPCs and chests before you reach it. Crossing a gap only changes which map the player is in: the new zone's camera `adopt`s the exact screen position the old one had (nothing moves on screen), the old zone stays drawn beside it, the hero's drawing (`Character.pivot`) eases up to their new place (the arrival cell is `1 + ARRIVE_CELLS` ahead of the door), the last zone's weather fades out over `WEATHER_FADE` as the new one's fades in, and `AreaBanner` names the new area. A zone seen from the next one over is a lookout (`ZoneState.setLookout`): its weather is hidden, and on a solo game or a host its mobs are drawn and kept wandering (the scene updates them with no one to chase) so nothing looks frozen or pops in as you cross; a guest, who is not told what they are doing, hides them. `Zones.prefetch` loads the zones joined by a gap when a player is within `BORDER_REACH` (30 cells) of the neighbours' margin (`nearBorder`), and `retire` keeps them (and every zone shown) loaded. A guest does the same on `follow`. Everything else (a shop or cave door, a trial, waking after a defeat) is the **iris**, one look: `map/transition.ts` (Pixi-free, tested). A black screen with a round hole closes on the hero in the old view (a still picture of the stage taken just before the swap), stays black a beat (or as long as a zone still loading needs), then opens round the hero in the live new zone, which settles in from a 12% closer shot (`Camera.punch`, `settleAt`) while the rim of the circle glows in the colour of the zone being entered (`zoneTint` in `systems/places.ts`, `rimAlpha`); about 0.9 s. It is drawn as a thick stroke rather than a rectangle with a hole cut in it: a `cut()` hole that crosses the rectangle's edge, as a circle larger than the screen does, draws solid black and flashes the screen. Do not add another look: a new door either joins two open-air zones by a gap (seamless) or uses the iris. `entities/ZoneTransition.ts` draws it over the stage (the scene's `root` is `top` = stage + transition); the local player stands still and takes no door while it plays. Purely visual: the simulation moved the player at once, so it is the same for solo, host and guest. **Co-op**: players can be in different zones at once. The host simulates every occupied zone and sends each friend a snapshot of *their* zone only (`SnapMsg.zone`, plus `away`: the slots of players in other zones, so they are not mistaken for having left; mobs, chests and events are that zone's; friends in the same zone share one built snapshot per tick). A guest that finds itself in a new zone (`followToZone`) loads it if needed (the iris closes on the old zone and holds shut meanwhile), plays the same transition, moves its own body there and re-places the others from the list. Events carry their zone (`emit`). `tools/map/check.ts` `checkDoors` (run by `npm run map -- check`) fails a door to a missing zone, one arriving on a wall or another door, or with no door back. Interiors are built by `tools/map/interiors.ts` (`shopInterior`) from `interior.png` (floor, wall, doormat, counter, shelves, signs), drawn by `tools/map/interior.ts` (part of `npm run tilesets`) in the shop buildings' palette; the town's door cells are `SHOP_DOORS` in `maps/town.ts` (world cells), which the shop rooms read through `shopExit` (in the town's own cells). `checkDoors` runs over the biomes too. **`checkCrossings` (also in `npm run map -- check`, with `tools/map/walk.ts`) walks the real collision box through every directional door: the arrival fits, the way ahead stays open for 6 cells (no bush in the doorway) and a body can walk 30 cells on (or reach the spawn), so no crossing drops a player into a pocket.**

- **Economy: gold, pack and shops** — `Hero` has `gold`; the pack is the Inventory's `hero.pack` (capped, see above), and supplies like potions live in it. Every `Item` has a `value` in gold (the campaign's items.json, see Content); supplies (`potion`, `elixir`) have no slot and a `use` (HP/MP restored) and are drunk with the Inventory screen's Drink button. The shop-side pack moves are at the end of `systems/inventory.ts`: `wearIfBetter` (puts a piece on and sends the old one to the pack), `wearFromPack`, `useFromPack`, `packEntries` (grouped), `isBetter`/`upgrade`. **Money comes mainly from enemies**: each `MobKind` has `gold`, rolled ±30% by `rollGold`; `OverworldScene.hitMob` gives every player the same purse on a kill (like XP) and floats `+Ng`. Chests can also hold gold (`coins`/`purse`/`hoard`). `systems/shops.ts` (Pixi-free, tested): `SHOPS` (content, items.json `shops`): in campaign 1 five specialists, each with a `keeper` (an `NPC_LOOKS` key), `stock` and what it `buys` (`shopBuys`) (a shop buys back only its own trade, at `SELL_RATE` 40% of `value`): `smithy` (swords, shields), `armory` (helms, chest, legs), `ranger` (bows, boots, cloak), `apothecary` (potions, elixirs), `wizard` (wands and tomes, bought back too; the smithy no longer takes them). `buy` wears gear that beats what the hero has, else puts it in the pack, and refuses (taking no gold) when there is no free pack slot. **Chests no longer hold what a shop sells**; they keep the rare pieces (Viking Helm, Legion Armor, Parrying Dagger, elixir) and purses. Keep a piece in one place: stock in one shop, or chests. Shopkeepers stand inside the shop rooms (`z.shop(id, col, row)`, `MapData.shops`, checked by `tools/map/check.ts`); the building outside is `z.prop('smithy'|...)` with a `z.door` into the room. In `OverworldScene` the action key within `KEEPER_REACH` (2.3 cells, across the counter) of a keeper opens a greeting `Dialog` (its `say(lines, onDone)` runs `onDone` after the last line), then `hud/ShopCounter.ts` (`#shop` in `index.html`: Buy/Sell tabs, Wear/Drink buttons) — a modal like the menu: solo it pauses the world, online it only freezes the hero. The shop counter's Sell tab also has Wear/Drink buttons (`ShopCounter.onGearChange` makes the scene redraw the hero). `Hud` shows gold, the Status tab too. **In co-op every player is their own character**: the host keeps each friend's whole `Hero` (stats, gold, pack, gear) and is the only one who changes it. A friend's wishes travel as `do` messages (buy/sell/wear/use + an item code, built by `systems/trader.ts`'s `remoteTrader`; the menu and shop counter talk to a `Trader` and don't know whether it is `localTrader` or remote); the host's `handleTrades`/`tradeFor` check them (known item and shop, the friend in that shop's room within reach of its keeper) and answer with a `pack` message (gold, worn item codes, pack, plus `say` = the reply to show once). `pack` goes to each friend on change and once a second, and `looks` (what every player wears) goes to all, so everyone sees everyone's gear. Item codes are `itemCode`/`itemFromCode` in `systems/inventory.ts` (an item's index in the campaign's items.json plus one): adding an item at the end of a campaign's list is safe, reordering it is a protocol change for that campaign. A guest's Inventory screen works like the host's (its actions go to the host as `InputMsg.inv`, see Inventory); a friend's character exists only for that game: their solo hero is put back when they leave (`OverworldScene.solo`).
- **Signposts at the forks of the roads** — `systems/signs.ts` (Pixi-free, tested): a biome spec calls `z.sign(col, row, ways)` at each fork of its trails (`ways`: `up`/`down`/`left`/`right` → a zone key, named through `ZONE_NAMES`, or a `z.place` name on the same map); in a biome it stands on the free cell nearest that point that is beside a road but not on it (`BiomeWindow.sign`), as the solid `signpost` prop (drawn by `tools/map/interior.ts` on `interior.png`), and lands in `MapData.signs`. `checkMap` fails a sign with fewer than two ways, an unknown destination, or no reachable cell beside it. A sign is read **like talking to an NPC**: in `OverworldScene.handleAction` the action key within `SIGN_REACH` (1.5 cells of its foot; `signNear`) opens it whichever way the hero faces (before shopkeepers, givers, pets and the NPC, and before a swing), and the hero turns to face the board; the dialog is one page, a line per way with its arrow and compass point (`signLines`, "↑ North: The Barrow Lands"; `#dialog p` keeps the line breaks). Every fork of the open-air world has one (the town's streets end in the market, and the desert and the Mirewater have one trail each). **Co-op**: local reading of map data like the lectern; nothing on the wire.
- **Pets (dogs, cats and a rat)** — `systems/pets.ts` (Pixi-free, tested): `PET_KINDS` (four dogs on `public/sprites/pets/dogs.png`, four cats on `cats.png`; 32px frames, four columns per animal, rows right/up/down/left, column 3 = lying; the `rat` on `rat.png` has 3 columns, rows down/left/right/up, no lying frame, its tail twitches through `idleFrames`: each kind carries its own `rows`/`cols`), what each says (`petSound`: dogs woof, cats meow) and `petPose`/`petFrame`. `PetBrain` (same file, Pixi-free) is their behaviour: stand, lie down (not the rat), or amble to a spot within `LEASH` (5 cells) of where they were placed, each step checked against the zone's collision (`kind.speed`). `entities/Pet.ts` draws one; `attend` stops it and turns it to the player. Zones place them with `z.pet(kind, col, row)` (`MapData.pets`, checked by `tools/map/check.ts`; they do not block); the town has ten, every biome one to two (dogs, cats, and rats in the swamps and jungle). In `OverworldScene.handleAction` the action key within 1.5 cells of a pet makes it answer in the dialog (before the NPC, after shopkeepers). **Co-op: pets are local scenery like the NPC** (each player's pets wander independently, so they are not in the same spot on two screens; the talk is a local dialog; nothing goes over the wire). Art source/licence: see CREDITS.md.
- **Shop buildings** — `public/tilesets/town.png`, built by `tools/map/town.ts` (part of `npm run tilesets`) from the CC0 "Town RPG Pack" by Luis Zuno in `art/town_rpg_pack/` (16px art, doubled to the 32px grid): the pack's inn and tall house are cut out, roofs recoloured, the tall house given the inn's door, and an emblem painted over each door. Coordinates are `BUILDINGS` in `tools/map/catalog.ts`; the prefabs `smithy`, `apothecary`, `wizard` (6x7 cells) and `armory`, `ranger` (3x9) are solid from the ground up. Each building has a door (see Zones and doors) into its shop room.
- **Treasure chests** — `systems/chests.ts` (Pixi-free: `CHEST_KINDS` = rows of `public/tilesets/chests.png`, `CHEST_LOOTS` (the campaign's items.json `loots`), `collect(hero, loot)`: gear is worn if its slot is empty or it is an upgrade (the old piece goes to the pack), otherwise it goes to the pack, and a full pack leaves the chest shut; potions, XP and gold also work) and `entities/Chest.ts` (open/closed sprite, origin at feet). Zones place them with `z.chest(kind, loot, col, row)` (solid cell; `MapData.chests`, checked by `tools/map/check.ts`). In `OverworldScene` the action key opens a closed chest within `CHEST_REACH` before it swings (`act`); only solo/host decide, and the host sends opened chests to guests as a bitmask (`SnapMsg.chests`, max 30 per map). Guest gear sprites are not synced.
- **Slippery ice**: `systems/ice.ts` (Pixi-free, tested): `isIce` reads the `ice` surface under a player's feet and `stepVelocity` eases `Player.vel` toward the held direction (grip `ICE_ACCEL`) and coasts when keys are released (`ICE_DRAG`); off ice velocity equals the walking velocity, so normal movement is unchanged. Applied to players in `OverworldScene.move` (host/solo; guests only see positions); mobs ignore it. The ice tiles are painted (cracks, glints) by `tools/map/recolor.ts` into the empty corner of `frost_ground.png`; the lake's ring cells keep the snow surface, so only the inner fill is slippery.
- **Weather** — each biome has its own (`systems/weather.ts`, Pixi-free, tested): a zone's `MapData.climate` (a key of `CLIMATES`, set by `defineBiome({ climate })`; rooms have none) says which precipitation can fall there: `temperate` (greenwood, eastwood, town: rain, storm), `coast` (beach: rain, storm, windier), `desert` (sandstorms only), `jungle` (heavy rain and storms), `swamp` (wetlands, marsh: rain), `undead` (ash, storms) and `frost` (snow, blizzards; snow falls nowhere else). A `Weather` (one per `ZoneState`) keeps **precipitation** (`Precip`: rain, storm, snow, blizzard, sand, ash, or none) and **wind** (`windLevel`: none, a breeze or a gale, plus the precipitation's own `LEAN`; direction ±1) separately: `CLEAR_SHARE` (80%) of the time there is neither; otherwise it is precipitation alone, wind alone, or both. Spells last 90-180 s, clear or not, so the time share matches, and ease in and out over 6 s. Only zones with a player in them are advanced (`Simulation.weather`, in the per-zone loop; a zone that is unloaded starts afresh, and a new `Weather` starts at a random point of a spell), and lightning is rolled there too (`Weather.strikeDue`, only in a built-up storm; the bolt lands around a random player *in that zone*: a `lightning` world event, and a player within `LIGHTNING_RADIUS` takes 35% of their max HP). `entities/WeatherLayer.ts` only draws a `Weather` (a haze for some, a pooled field of streaks/flakes/grains/ash in one `ParticleContainer`, gust streaks for wind alone, a flash and a seeded jagged bolt); the layer is part of its zone, so in a door transition each biome's sky is pushed in with it. Wind blows leaves (`Ambient.wind`). Weather is a backdrop and must stay cheap: no full-screen frame or heavy dimming (a full-screen haze layer is the costliest part; snow has none), and drops are placed by a low-discrepancy sequence (`Drop.u/v`) so they spread evenly instead of clumping. **Co-op**: the host rolls every occupied zone's weather and sends each friend *their zone's* in the snapshot (`SnapMsg.w`: `[precip index + 1 or 0, wind %, intensity %, 1 if it blows right]`; `Weather.snapshot`/`setRemote`); a guest never rolls its own. Dev/playtest: `scenes.current.setWeather('rain', 0.85)` forces weather in the zone you are in (`setWeather(null, 0.35)` is a breeze alone).
- **Day and night** — `systems/daynight.ts` (Pixi-free, tested): the time of day is 0..1 (0 midnight, 0.5 noon), `DAY_LENGTH` (12 real minutes) per day, and `skyColor(time)` interpolates the `SKY` stops (just day, night and a short blend between) into a multiply tint. `DayClock` reads the **wall clock**, so every co-op player sees the same hour with nothing on the wire (no protocol change). `entities/NightLayer.ts` is one screen-sized sprite with `blendMode: 'multiply'`, in the scene root over the stage and under the quest arrow and door transition; it hides itself in rooms (`MapData.indoor`) and in full daylight. Purely cosmetic for now. Dev/playtest: `scenes.current.setHour(22)` jumps this client to an hour.
- **Ambient life**: `src/entities/ambient.ts` is passive background animation driven by body movement and map metadata (no hooks into collision): footprints that alternate feet and fade within 2-3 s, only on soft terrain (`PRINTS`: `sand`, `snow`, and `puddle` once a puddle ground exists; hero and mobs; pooled, capped at 96), and leaves that drop when the hero moves behind a canopy (a `tree`/`bush`-tagged object drawn over the hero) or swings at one (`Ambient.shake`, called from `OverworldScene.attack`). Leaf colours follow the canopy's sheet name (`trees_green/frost/dry/jungle/dead/swamp.png`, `PALETTES`). It parents everything to `world.layer`. To add an effect, keep it pooled and capped, and key it off `surface`/`tag`/`level` rather than coordinates.
- **`src/map/`** — `types.ts` (`MapData`, `parseMap`) and `MapView.ts`: a render group with a `ground` layer and a y-sorted `layer` holding map objects (cullable via `CullerPlugin`) plus everything the scene adds (characters, effects). **It streams**: the map is cut into `CHUNK` (16) cell chunks (`map/chunks.ts`, Pixi-free, tested) and `update(view)`, called every frame after the camera moves (and by `Zones.show`), builds the chunks round the view (each chunk's ground its own render group, its objects added to `layer`) and frees the ones left two chunks behind, so a big zone costs about what a small one does; only the map data stays. Add entities to `world.layer`, never to the `MapView` itself, and don't rely on a map object's sprite existing.
- **`src/assets.ts`** — all loading goes through the Pixi `Assets` manifest: the sprite part manifest (the part layers used at boot are loaded by `Wardrobe.load` as images, see Characters) and per zone `loadZone(name)`: the map JSON, read by `parseMap`, then the tilesets it names, each loaded once under `tileset:<file>` and counted per zone using it, so `unloadZone(zone)` frees exactly the sheets no other loaded zone needs. Every URL under `public/` the game fetches (maps, tilesets, `parts.json`, part layers) carries `?v=<hash of that file>` from `virtual:asset-versions` (`tools/assetVersions.ts`, a Vite plugin that hashes `public/maps`, `public/tilesets` and `public/sprites/lpc` at build time; empty in the dev server), so a deploy never pairs new code with a cached old map or sheet, and a file that did not change keeps its URL and stays cached. A new folder of fetched files goes in `VERSIONED_DIRS`. `__BUILD_ID__` is only the co-op version handshake. Don't call `Assets.load` ad hoc elsewhere (the `Wardrobe` is the one sanctioned exception, for sprite layers, which it loads as `<img>` elements).
- **HTML overlays** (`src/hud/`; markup in `index.html`, styles in `src/ui.css`): `Hud.ts` (HP/MP bars), `Dialog.ts` (`#dialog`; tapping it advances; `layout()` keeps it clear of the touch controls), `Menu.ts` (pause menu: Status / Inventory / Controls / Online, plus Trade while online, with Credits as a lone tab in the bottom-left corner; the Online tab is `Multiplayer.ts`, which only drives the `Session`) and `MapOverlay.ts` (the co-op map, below) and `Loading.ts` are DOM rather than Pixi so text stays sharp on phones and can use safe-area insets.

To add a button, add a `data-key` element.
- **Map pipeline** — maps are built by agents from code, not painted: **use the `build-zone` skill** (`.claude/skills/build-zone/SKILL.md`) for any map change.
  - `maps/<zone>.ts` (source of truth) uses the `Zone` builder (`tools/map/zone.ts`: `fill`, `patch`, `forest`, `prop`, `stamp`, `plateau`, `block`/`unblock`, `spawn`/`npc`/`mob`) with named assets from `tools/map/catalog.ts`. `npm run map -- build` compiles it to `public/maps/<zone>.json`, renders `maps/out/<zone>.png` + `.debug.png` (gitignored), and runs `tools/map/check.ts`. Never hand-edit the JSON; `npm run build` fails if it's stale or a check errors.
  - The JSON is a packed `MapData` (`PackedMap` v3 in `src/map/types.ts`, written by `tools/map/encode.ts`: ground cells index a palette of shared layer stacks, objects are `[part, px, py]` triples into a parts table; `parseMap` unpacks it, and still reads the older v2). `MapData`: 32px ground cells referencing 32x32 regions of tileset sheets (a cell may stack several `[sheet, x, y]` layers, bottom first: terrain edges drawn over the ground; `MapView` and the previews draw them in order), free-placed objects (y-sorted by bottom edge, or by an explicit `z` for flat art like cliffs; each can carry a `tag` such as tree/bush/rock/cliff), a collision cell list, per-cell terrain metadata (`surface` names like grass/sand/snow, `level` height, `ramps` = stairs) for game systems, spawn/NPC cells and mob spawns. The game reads collision, surface (footprints) and tags (leaf fall); `level`/`ramps` are for height-aware movement (see Roadmap). `MapView` renders it in the game; `tools/map/image.ts` renders the same way in Node for previews. Tilesets live in `public/tilesets/`; all art is cut on the 32px grid.
  - **Cliffs**: `z.plateau(rect, {kind, stairs})` builds a raised plateau from the Avalon blob on `Cliff_tileset.png` (cut along its grass hole so it scales to any size >= 4x4; measurements in `CLIFF`, `tools/map/catalog.ts`). `rect` is the walkable top; the rim ring and two face rows around it block; stairs are the only way up and become `ramps`. `kind` picks `grass`/`frost`/`dry` (`frost_cliffs.png`, `dry_cliffs.png`, derived in `recolor.ts`). The top is always the ground its rim is drawn with (`TOP_GROUND` in `zone.ts`: grass, snow, sand): `plateau` fills it and no terrain shows on it, painted before or after (a mesa in the desert's red dirt used to show a red middle inside a sand rim). The art is flat ground-level (`z` below all entities), so the hero draws over it. `check.ts` fails if two open cells of different level touch without stairs (a gap in a rim). `Extra_Unfinished4.png` (stone wall, door, brown drop-off) and `graphics-tiles-waterflow.png` (animated water) are still uncatalogued.
  - Collision for props is derived from their art (cells covered by the bottom `solid.band` px of the sprite), forests block their rect, so collision tracks the visuals. The tilesets have no foliage edge tiles — all vegetation is prefabs, and trees are cut from the LPC trees pack (see Trees and bushes).
  - **Terrain (autotiled ground)**: `z.paint(terrain, rects)` paints a terrain on cell *corners* from the LPC terrain atlas (`public/tilesets/lpc_terrain.png`, "Tiled Terrains" from OpenGameArt, source + Tiled tileset in `art/lpc_terrain/`; `tools/map/terrain.ts` reads which tile has which corners from `Terrain.tsx`), so any shape blends with soft edges and inner corners (dirt roads, sand, mud, ash, swamp water, ponds, ice, lava, pits...). Terrains stack over the cell's `fill` in `TERRAINS` order; the opaque `coast`/`snowCoast` bring their own sea. The atlas also gives full-cell grounds (`sea`, `cobble`, `flagstone`, `crackedStone`) and props (sandstone/basalt boulders, a standing stone, reeds, lily pads). `blob`, `pond`, `trail` and `reedsAt` in `tools/map/helpers.ts` make organic patches, ponds, winding trails and bank-side reeds; `tools/map/noise.ts` has the noise, `smoothMask` and `distanceField` that shape pools and ground edges. **`murk`** is swamp water: the atlas's soft-banked pond recoloured olive (`lpc_swamp.png`, `SWAMP_SHEET`, made by `recolor.ts`; a terrain may name its own `sheet`). The atlas's `Sewer Water` tile is rectilinear (a dungeon sewer) and is not used for swamps. **Reeds** (`reedBed`, `reedStalks`) are bank plants: put them on the land beside water, never in it (the atlas draws a water-edge strip under them, which is not used). The marsh keeps them two cells clear of its causeways, and their two foot rows block like a trunk's.
  - **Trees and bushes** come from the LPC trees pack (`art/lpc_trees/`, CC-BY-SA, see CREDITS.md), not the Avalon sheet. `tools/map/treePicks.ts` lists the picked sprites (rects that enclose one sprite), `tools/map/trees.ts` (part of `npm run tilesets`) cuts each out by its shape (keeping its translucent baked shadow), packs them into `public/tilesets/trees_<green|dry|jungle|dead|frost|swamp>.png` (frost and swamp recolour the green sheet) and writes `tools/map/treeAtlas.ts` (generated, never hand-edit). Every kind has six trees `treeA`..`treeF` (`frostTreeA`.., `dryTree..`, `jungleTree..`, `deadTree..`, `swampTree..`) and two bushes (`bush`, `bushSmall`; `frostBush`...); `TREES`, `FROST_TREES`, `DRY_TREES`, `JUNGLE_TREES`, `DEAD_TREES`, `SWAMP_TREES` list them for groves, walls and `scatter`. Collision: the bottom 75% of a sprite (`SOLID_SHARE`), the crown above it is walk-behind; `isArt` ignores translucent pixels so shadows never block. The leaf-fall (`entities/ambient.ts`) keys off the `tree`/`bush` tag and the sheet name (`trees_frost.png` → frost leaves), so a new kind needs a `PALETTES` key in its file name. To add or swap a tree, edit `treePicks.ts`, run `npm run tilesets`, then `npm run map -- build`.
  - **Recoloured sheets**: the Avalon pack only has grass/sand/water/stone, so snow and ice are *derived* sheets (`frost_ground.png`, `frost_objects.png` (blue-grey rocks), `ground_plus.png`) generated by `tools/map/recolor.ts` (`npm run tilesets`, outputs committed). Same coordinates as the originals, so catalog entries just point at another sheet; each has its own baked shadow colour (`SHADOWS`).
  - **World (the biomes)**: `maps/world.ts` lays the open-air world out after the hand-drawn map, one character per 10x10-cell square (34 x 23 squares = 340 x 230 cells), and lists the **gaps** between biomes. The borders don't follow the squares: `carve` (tools/map/world.ts) pushes each cell's lookup about with smooth noise (`wobble`, default 0.7 squares; `seed`), smooths away spikes and gives stray islands to their neighbour, so borders look carved, but runs them straight across every gap. Each biome is a `maps/<name>.ts` that default-exports `defineBiome({ name, climate, walls: { trees, fillers }, worldEdge?, build })` (`climate`: its weather, see Weather) and builds in *world* cells, placed in squares through `units(square)` (`at`, `area`) so the content scales with the layout. `buildWorld` (run by `npm run map`) walls every biome in along every border and the world's edge with `WALL` (3, a round band) cells of its own `woods`, cuts a 3-wide corridor through both walls at each gap (and keeps the way just past it open) with a door on each side leading straight across (`dir` set, arriving `ARRIVE` cells in), runs every spec, composes them into one world (`Zone.compose`: each cell from its owner; a see-through terrain fades across a border) and cuts each biome's map from it: its own cells plus `MARGIN` (14) cells of its neighbours, blocked (surface `beyond`); the game does not draw them in this zone's view but lays the neighbour's own map there (see Zones and doors), so the wall seen across a border *is* the neighbour's wall and the margin tells the game how the two maps line up. Pockets of open ground nobody can reach from the spawn are sealed. **Edges are never straight**: a wall's inner edge swells by up to `RAGGED` cells with noise on top of its `WALL` core (`World.wall`, from `World.borderDistance`, the distance of each cell to the nearest other biome); `z.ground(terrain)` lays a biome's ground terrain over its own cells but stops `inset` cells short of the borders (default 3 to 7, wandering), so the grounds on either side of a border never meet in a straight line (use it instead of `z.paint(terrain, z.bounds)`); pass `inset: [1, 2]` so the edge lies under the walls rather than leaving a ring of grass inside them (the Barrow Lands' ash). **Jarring ground fails the build**: `tools/map/ground.ts` (`groundReport`, run by `checkMap` on every open-air map, tested in `check.test.ts`) measures the floor as it is drawn (ground layers plus cliff art, Lab colour): a *hard seam* is a colour jump right on a cell boundary (`SEAM_STEP`; autotiled edges change colour inside the tile, so they pass; a fill against a fill, a paved rect, a plateau top unlike its rim, the sea against grass do not), and a *clash* is one surface in two shades further apart than `CLASH_DE` within two cells (a deep green over a pale grass). Seams under props, the edge of cliff art on open ground and the drawn banks of ponds, bogs, lava, pits and ice are exempt. Paved spots use `z.patch('stone', rect)` (its own grassy edge), not a `fill` blob; the desert and beach lay soft `sand` terrain over their base so they fade across borders; `redDirt` is its own surface (`clay`). **A biome's ground is a palette of at most two**: two grounds may share a biome if their colours are close and the edge between them is soft (an autotiled terrain edge, a shape from `blob`/`z.ground`, never a bare rect or a cell-stepped line). The LPC `meadow`/`darkGrass` are too far from the Avalon `grass` fill to pair with it, so the green biomes use `grass` alone for now (the cliff art's grass, so plateaus match: a plateau's top must be the ground it stands on); a palette-matched second grass would be a terrain recoloured to sit beside `grass` (`recolor.ts`, as `murk` is); a `grove` never grows onto a road (cells kept clear, plus one of verge) and `scatter` keeps a tall prop's canopy rows off a road too. Maps include `MARGIN` (22) cells of the neighbours, more than half of a 1280 px wide view. **`checkSeams` (tools/map/check.ts, run by `npm run map -- check` and the zone test) enforces that borders match**: along every border both sides are blocked, or both are doors straight across to each other, and nothing is open on the world's edge. The beach sets `worldEdge: false` and closes the north with the sea. **Woods** (`z.grove(area)`, and the walls) are any shape: trees standing wholly inside it on a staggered lattice, then fillers for the corners, and its cells block only where that art covers them (`SOFT_COVER`; the row along a border always), so the edge of a wood is as walkable as it looks. **No invisible walls**: a wall plants 55% of its lattice (`WALL_DENSITY`), but every cell of its border row gets a tree, else a bush or rock (`woods`), so each side of every border shows its own line of trees; a border cell nothing fits over is marked `BARE_WALL` and fails `checkMap`. Shapes come from `blob` (a lobed outline), trails from `trail` (winding between nodes, straight into a gap's corridor `worldOf(layout).gap(a, b)`), points from `z.near(col, row)` (the nearest free cell, whatever the border did). A biome spec also gets `bounds`, `owns`, `keepClear` and a deterministic `scatter`. Plan against `npm run map -- layout <biome>`; keep a gap away from a bend of its border. Snow and sand both blend into grass.

## Working procedure (rapid dev mode)

The project is in rapid development, and this is how every session (Claude or human) works until the maintainers say it has matured:

- **Push to `main` before the full test suite, then fix forward.** Do not wait for `npm run build` or `npm run test:e2e` (the e2e suite takes 10+ minutes) before pushing to `main`. Push, then run them, and if something fails, fix it in a follow-up push. The game is a static single-page site, so a bad push cannot take anyone's running copy offline; other developers getting current code quickly matters more than a gate. A failing check after a push is the next thing to fix, not a reason to revert unless it makes the game unplayable.
- **Merge `main` in first, and often.** Drift is the real cost: fetch and merge `origin/main` before starting work and again right before pushing, and resolve conflicts then rather than leaving them for a PR. Keep changes small and push them as soon as they are coherent. Prefer a fast-forward push to `main` when the branch already contains it.
- **Hooks enforce the merge rule** (`.claude/settings.json`, scripts in `.claude/hooks/`): at session start `sync-main.sh` fetches `origin/main` and merges it into your branch when that is clean (it reports, and leaves the tree alone, if it conflicts or you have uncommitted changes); when a session ends `check-main.sh` blocks once if your branch has commits that are behind `origin/main`, telling you to merge now. They do nothing offline, on `main`, or on a detached HEAD.
- **Still cheap and worth doing before a push**: `npm run typecheck` and the unit tests (`npm run test`, seconds). If a quick check fails, fix it before pushing; do not skip it just because the full suite may be skipped.
- **Two things are not covered by "it cannot go offline"**: the matchmaking relay (`relay/`) is a live Cloudflare Worker that redeploys from `main`, and the game and relay deploy a minute or two apart. A change to `relay/` or to the relay API (`src/net/relayApi.ts`) can break everyone's co-op setup, so test those first. A protocol change (`PROTOCOL_VERSION`) makes players on the old page unable to play with players on the new one until they reload; that is expected, but say so in the commit.
- Never commit secrets or private assets (the repo and site are public), whatever the pace.

## Conventions

- **Name the layer** (see Where a feature belongs): every new feature is core engine, a capability, content or a pack section, and its bullet in this file says so. A system a story could do without is a capability from the start; a new kind of thing in the world is content, never an id in `src/`.
- **Keep multiplayer in sync with single player.** Co-op is not an afterthought: whenever a feature touches gameplay state (stats, gold, pack, gear, shops, chests, combat, mobs, map objects, a new key or menu tab), decide how it behaves for the host and for a guest *in the same change*. The host owns every hero and all simulation; a guest only sends wishes (`do`, `tr`, input) and renders what it is told (`snap`, `pack`, `looks`, `trade`). If something is solo/host-only for now, say so in the UI (e.g. the guest's "kept by the host" note) and in this file. Anything new that a guest must see goes through `src/net/protocol.ts` (validated in `parseMessage`, version bumped, a `protocol.test.ts` case) and `session.ts`; anything new that needs a guest's input is a numbered/ackable command, not a raw event. Add unit tests for the pure rules and an `e2e/multiplayer.spec.ts` case when a flow spans two players. **When you change a single-player system, update the co-op bullets above (and the matching ones in the other direction) so this file always describes both.**

- TypeScript is strict plus `noUncheckedIndexedAccess` and `verbatimModuleSyntax` for game code (`tools/` indexes freely). Prefer a clear error over `!` when data can be missing; `!` is fine for DOM lookups that `index.html` guarantees.
- Prettier owns formatting (single quotes, width 120); ESLint is type-aware and bans floating promises.
- New rules/maths go in a Pixi-free module with a `*.test.ts` beside it.

## Deployment

The relay (`relay/`) deploys separately: Cloudflare builds and deploys it from `main` itself (no GitHub workflow); see `relay/README.md`. A relay change only reaches players once that build has finished, so wait for it before relying on a new API.

`.github/workflows/deploy.yml` builds and publishes `dist/` to GitHub Pages on every push to `main` (repo Settings → Pages → Source must be "GitHub Actions"). `vite.config.ts` sets `base: './'` so asset URLs work under the `/<repo>/` subpath — keep asset references relative (put static files in `public/` and don't use root-absolute `/...` paths).
