# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A top-down RPG built with PixiJS v8 + Vite + TypeScript. The repo and the deployed site are fully public, so never commit secrets or private assets. Deployed as a static site to GitHub Pages.

## Direction

The game is intended to become Zelda-like: real-time action combat, item collection, and progression (leveling skills, weapons/armor, magic). The code is split into scenes, systems and entities (below); next up are more zones with map transitions, items/inventory and more enemy kinds. Art, story and gameplay are iterated on incrementally.

## Commands

- `npm run dev` — Vite dev server with HMR (also exposes `window.__game` for playtest scripts, dev only)
- `npm run build` — typecheck, `map -- check`, `sprites -- check`, then production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run verify` — everything CI runs except the build and browser tests: lint, format check, typecheck, unit tests, map check, sprite check. **Run it before committing** when it is quick; see Working procedure for what must not block a push.
- `npm run lint` / `npm run format` / `npm run format:check` — ESLint (type-aware) and Prettier (`.ts`/`.json`/`.yml`; CSS, HTML and Markdown are hand-formatted)
- `npm run test` — Vitest unit tests (`src/**/*.test.ts`, `tools/**/*.test.ts`)
- `npm run test:e2e` — Playwright smoke tests against the production build (set `PW_CHROMIUM` to a local Chromium, e.g. `/opt/pw-browsers/chromium-*/chrome-linux/chrome` in cloud sessions)
- `npm run typecheck` — typecheck only (game, `tools/`, `e2e/`, `relay/`)
- `npm run relay` — the matchmaking relay in memory on `http://localhost:8787` (use with `VITE_RELAY_URL=http://localhost:8787 npm run dev` to try online play locally)
- `npm run map -- build|check|render|layout …` — zone specs → map JSON + previews + checks; `layout <biome>` prints a biome's walls, gaps and open ground (see Map pipeline)
- `npm run sprites -- build|check|preview …` — LPC part catalog → packed layer sheets (see Characters). `build` needs a clone of the LPC generator (`LPC_DIR`); `check` (run by `verify` and `build`) does not

CI (`.github/workflows/ci.yml`) runs `verify`, `build` and the e2e tests on every pull request; the deploy workflow runs `verify` before publishing.

## PixiJS skills

Vendored in `.claude/skills/` (`.agents/` is a gitignored duplicate). **Before changing anything in `src/` that touches PixiJS, load the `pixijs` skill** and follow the sub-skill it routes to (application, assets, scene-*, ticker, performance, math). Only the sub-skills this game uses are vendored; for anything else the router falls back to the live docs (`https://pixijs.download/release/docs/llms.txt`), or re-add a skill with `npx skills add pixijs/pixijs-skills`. Project conventions that follow them: `TextureStyle.defaultOptions.scaleMode = 'nearest'` and `resolution: devicePixelRatio` + `autoDensity` are set once in `main.ts` (don't set scale modes per texture); dynamic in-world text uses `BitmapText` with the pre-installed `FloatText` font, not `Text`.

Other project skills: `build-zone` (any map change), `add-mob-kind` (new enemy), `add-sprite-part` (new hair/armor/weapon/monster part), `add-particle-effect` (new/retuned particle effect), `playtest` (run/screenshot the game in a browser).

## Architecture

Pixi-free logic (rules, collision, camera maths, map format) is kept separate from Pixi code so it is unit-tested without a browser; keep it that way.

- `src/main.ts` boots: creates the PixiJS `Application` (async `app.init`, wrapped in a `void` IIFE — avoid top-level await), registers the manifest, loads assets behind the loading overlay, creates the shared DOM UI (`Hud`, `Menu`, `Dialog`, touch controls) and starts a `SceneManager` with an `OverworldScene`.
- **`src/core/`** — engine plumbing. `Scene.ts`: the `Scene` interface (`root`, `enter`, `update(dt)`, `resize`, `exit`) and `SceneManager` (runs one scene from `app.ticker` with a clamped dt, forwards resizes, and always calls `input.endFrame()` after each update). `camera.ts`: integer zoom chosen from the window size and a follow/clamp offset (`pickZoom`, `followOffset`, `limitOffset` are pure; `Camera.follow` also takes `EdgeLimits`, see Zones and doors). `input.ts`: module-level keyboard + mouse singleton (`isDown`, one-shot `wasPressed`; mouse buttons are `Mouse0/1/2` codes and count only when a real mouse presses the canvas; `isHeld`/`wasHit` are keyboard+mouse only, `isTouched`/`wasTouched` on-screen buttons only; `captureKey` hands the next key to the rebind UI; ignores keys typed into text fields, so pasting a code can't move the hero). `bindings.ts` (Pixi-free, tested): the rebindable controls, two slots per action (`up/down/left/right/attack/inventory`; defaults WASD/arrows, attack = left click or Space, inventory = I; there is no magic key: spells are combos, see Wands, tomes and combos), saved in localStorage; menu/map keys (Esc, Tab, M) are `FIXED_KEYS`, reserved and never hard-coded elsewhere: ask `menuPressed()`, `mapPressed()` and `tabStep()` (left/right *as bound*, so the move keys and the D-pad also flip the tabs of an open menu or shop counter). `tools/ui/touchKeys.test.ts` checks that every `data-key` in `index.html` is a code the game listens for. `controls.ts` joins them to `input` (`actionDown`/`actionPressed`; the on-screen buttons always work too). Game code asks about actions, never raw keys, for movement/attack. The editor is `hud/Keybinds.ts` on the Controls tab, hidden while touch controls are active (no customizing on mobile). **Aim mode** (`aim.ts`, Pixi-free, tested; the choice is saved in localStorage and set on the Controls tab by `hud/AimSetting.ts`): `move` is the original (shots go the way you last walked), `mouse` aims at the pointer: `input.pointer()` is the mouse over the canvas or, on touch, the spot last tapped; `controls.pointerAim(heroOnScreen)` turns it into a unit vector that rides in `Command.aim`. `Simulation.move` sets `Player.aim` (and `mouseAim`) but the hero keeps facing the way they walk; only an attack or a spell turns them toward the mouse (`faceAim`), so range, speed and damage are unchanged. A guest sends it as `InputMsg.am` (1..`AIM_STEPS` directions round the circle; absent = walk aim) and the host decodes it in `HostLink.command`. `touch.ts`: on-screen controls (below). `textures.ts`: `makeFrame` and `sheetGrid`, a per-sheet cache of frame textures. `direction.ts` (facings: `Direction`, `DIRS`/`dirIndex` for the wire, `DIR_VEC`, `directionToward`) and `interp.ts` (`glide`/`approach`, the snapshot smoothing) are the Pixi-free bits the sprites, entities and `net/` all share. `direction.ts` (facings: `Direction`, `DIRS`/`dirIndex` for the wire, `DIR_VEC`, `directionToward`) and `interp.ts` (`glide`/`approach`, the snapshot smoothing) are the Pixi-free bits the sprites, entities and `net/` all share.
- **`src/scenes/OverworldScene.ts` and `src/scenes/overworld/`** — the overworld is a world of zones (`ZoneState.ts`: one loaded `MapData` with its mobs, chests, shopkeepers, ground items and effects). `OverworldScene` is only the conductor (about 380 lines): the frame loop, the HTML overlays (menu, dialog, shop counter, trade window, map) and what the action key does on the spot (talk to the NPC or a shopkeeper, open a chest, pick up, otherwise attack). **Put new code in the file that owns the concern, not in the scene**: `Arena.ts` (who is in the game: `local` is the player at this keyboard and `remotes` the friends by player number, player 0 being the host; the loaded zones; `role`, the clock, the `Weather`; and the **zone context**: the rules are written once and serve every zone, `arena.zone` is the zone being worked in and a per-zone loop wraps its work in `arena.inZone(z, ...)`, so `arena.mobs`, `.collision`, `.effects`, `.chests`, `.ground`, `.players()` answer for that zone), `Zones.ts` (loading zones, prefetching those behind doors, `travel` through a door with the iris/slide `ZoneTransition`, showing the local player's zone on the stage, and a guest following the host's zone), `Simulation.ts` (the rules, solo and host only: moving incl. ice, cooldowns and regeneration, sword/bow/wand and tome (`Casting.ts`), mob shots, damage from mobs and lightning, XP and gold, defeat; what a friend should see goes through its `emit`), `Visuals.ts` (draws slashes, bolts, arrows, numbers, particles, poses and lightning; the simulation and a guest both use it, `show(event)` is how a guest draws what the host reports), `Ground.ts` (items on the floor: drop, pick up, crumble, and a guest's synced list), `PackSync.ts` (gold, pack and gear: the local player's Inventory actions and trades, the host doing a friend's requests and sending packs, a guest applying them), `Trading.ts` (player-to-player trades: the host's `TradeBook`, a guest's command queue, the trade screens), `HostLink.ts` and `GuestLink.ts` (the two sides of the snapshot/input protocol, below) and `constants.ts` (shared tuning). A new rule belongs in `Simulation`, a new thing to draw in `Visuals`, a new thing that is synced in co-op in the matching link. Each frame the scene reads `Session.role` (`solo`/`host`/`client`, see Co-op); combat is per `Player` (`entities/Player.ts`: body + hero + cooldowns), driven by a `Command` from the keyboard or the network. Solo, a dialog freezes the world and the menu pauses it. New areas are new zones (or new scenes), not more code in the scene.
- **Wands, tomes and combos** — a wizard's shop (`shop_wizard`, door in the town, in the east beyond the ranger and clear of the north road) sells wands and tomes (`ITEMS`: `apprenticeWand`, `stormcallerWand`, `noviceTome`, `arcaneGrimoire`; `Item.focus`, a `Focus` from `systems/spells.ts`, Pixi-free and tested). They are weapons (main hand only; never auto-worn over a blade, see `isBetter`) whose plain attack is a free bolt (`Casting.basic`, as strong as the weapon's attack; a wand's cooldown is short, a tome's long) and which have **combos**: a string of four direction taps (`uulr` = W W A D, or the on-screen D-pad flicked up, up, left, right) that casts a spell for MP, much stronger than the plain attack (damage/healing = `spellPower` = magic stat + the weapon's `focus.power`, times the combo's `power`). Every combo of a weapon is the same length and distinct, and the same string may do another thing on another weapon; `spells.test.ts` checks at least three per weapon. `core/combo.ts` (`ComboReader`, Pixi-free, tested) takes the move presses (`actionPressed` up/down/left/right, so rebinding and the pad work; nothing counts while a menu, dialog or door transition is up; `COMBO_WINDOW` 0.7 s between taps) and yields the finished combo's index into `weapon.focus.combos`, which rides in `Command.combo`. `scenes/overworld/Casting.ts` carries the spell out (solo/host): `bolt`, `fan`, `chain`, `dash` (Blink), `nova`, `blast` (Meteor), `heal`, `ward` (`Player.ward`, immune and tinted); a spell that can do nothing (no target, nobody hurt) costs no MP. `hud/Hud.ts` shows the weapon's combos in `#combo-hud`, lighting the arrows typed so far; the Inventory and shop show them too (`hud/itemText.ts`). **Co-op**: the guest detects the combo locally and sends `InputMsg.cb` (a running counter) and `ci` (the index) like an action press; the host runs it on that friend's own weapon (`HostLink.command`); effects ride as the usual `bolt`/`text`/`fx` events (new fx `castGlow`, `nova`, `blast`, `zap`, `heal`, `ward`, `blink`; `castGlow` also tells a guest to play the cast pose) and `FLAG.ward` tints a warded player. **Skills (innate spells, the training wizard)** — `systems/skills.ts` (Pixi-free, tested): `SKILLS` are spells a hero carries (`Hero.skills` learned, `Hero.loadout` ready; not items, so they work with a sword, a bow or a wand), tapped like a combo (four directions, a full turn; never contained in any wand/tome combo, `skills.test.ts` checks) and weaker than a wand's spells. One new skill every five levels: **Arcane Edge** (level 1, 5 MP, `ruld`: the next 3 sword swings, arrows or wand bolts within 12 s add magic damage, `Simulation.takeEdge`, `Player.edge`), **Spark Volley** (level 5, 6 MP, `urdl`: a fan of three bolts, each at 0.7 of spell power, via `Casting.fan`; offensive, weaker than a wand's fan), **Iron Skin** (level 10, 8 MP, `dlur`: 8 s of taking 55% of damage, `Player.guard`, applied in `Simulation.harm`) and **Spirit Mark** (level 15, 9 MP, `ldru`: a pulse that stings foes within 4 cells and marks them for 8 s, every hit on them does 30% more, `Casting.marks`/`markFactor` in `Simulation.hitMob`); effects show as a tint (`auraTint`, `FLAG.ward/edge/guard` for guests). **Only two skills are ready at once** (`LOADOUT_SLOTS`; `learn` fills a free slot, `setLoadout` is the one validated way to change them): a wand or tome's own combos do not count toward the two, so a wand gives 2 skills plus all its combos. `heroCombos(hero, zone)` is the one list the combo reader, HUD and `Casting.combo` use (the wand/tome's combos first, then `activeSkills`; the index is what travels as `ci`); `activeSkills` puts **the skill being tested in slot 2 of its training ground** (`skillOfZone(zone)`, slot 1 stays), so it can be tried on the wave. The **Magic tab** of the menu (`hud/Magic.ts`, `#menu-magic`; the scene attaches `MagicHandlers` on `enter`) shows the two slots, what each skill does and its arrows, and buttons to ready/remove them any time (it also lists the weapon's combos). They are learned in **trials**: the trainer (`GIVERS.orin`, `z.giver('orin', ...)` in `shop_wizard`; the action key beside him reads `trainerTalk`, which explains the skill, the two slots, the Magic menu and that the skill is on loan in slot 2 during the trial; when the last line is dismissed the trial starts) sends the player through the iris to that skill's training ground (`maps/training_novice|apprentice|journeyman|adept.ts`, built by `tools/map/training.ts`: indoor zones, a doormat out at the bottom, enemies that do not come back, `Mob.respawns = false` for `isTrialZone`; the skill is the next unlearned one whose `minLevel` the hero has reached). `scenes/overworld/Training.ts` (host/solo) runs them: `start` (checks level and knowns, loads the zone, resets the wave, full HP/MP, `Player.trial`), `update` (every enemy down: each player in the zone being tested for it learns the skill, is told which slot it went to or how to swap, and is sent back after 3.5 s; walking out of the door gives up), `fail` (called from `Simulation.defeat`: a defeat in a trial wakes you in the trainer's room instead of the start of the world). The later trials' enemies (`chieftain`, `cultist` for level 10, `warlord`, `wraith` for level 15) are tuned for those levels (nothing in the open world hurts a level 10+ hero). `checkDoors` does not ask a trial zone for a door back. **Co-op**: a guest reads the trainer's lines locally (its hero's level, skills and loadout are synced) and asks the host with `DoMsg` op `train`; the host checks the trainer is beside them and starts the trial (the guest follows to the new zone like any door); the Magic tab's choices go as `DoMsg` op `loadout` (`item` = `loadoutCode`) and the host validates them; `PackMsg.skills` (`skillMask`) and `PackMsg.loadout` tell the guest what it knows and has ready. A **lectern** in the wizard's room (`systems/lectern.ts`, prop `lectern` placed by `maps/shop_wizard.ts`; the action key beside it opens a `Dialog` with a page per wand/tome listing every combo; local reading only, nothing to sync) shows all of them. Wands and tomes have no art on the hero yet (`look: {}`; the weapon vanishes in the cast pose anyway). The old right-click/K/B Time Bolt (`Hero.spell`) is gone.
- **`src/systems/`** — `combat.ts`: stats, gear, `MobKind`s/`MOB_KINDS` and the damage/XP/level-up rules (`newHero`, `rollDamage`, `gainXp`). Levelling is superlinear: `xpToNext(level) = round(20 * level^1.5)` and `levelGains(level)` (stat gains per level-up) steps up every 4 levels; mob XP is fixed per `MobKind`, so a new tougher kind is how higher levels stay meaningful. `particles.ts` (Pixi-free `Emitter` simulation with fixed pools) and `particleEffects.ts` (the effects, pure data; add one with the `add-particle-effect` skill). `collision.ts`: `Collision` (cell collision from the map plus body-vs-body blocking: characters block each other but can always move apart; per-axis `slide`).
- **`src/entities/`** — `Character.ts` renders the hero/NPCs/mobs from a composed *doll sheet* (below): looping idle/walk follow `animate(dt, moving)`, one-shot `play('slash'|'cast'|'hurt', ms?)` takes over until done, `setSheet()` swaps the look when gear changes. Its container origin is the *feet*, so collision and y-sorting (`zIndex = y`) use it directly. `Mob.ts`: enemy AI state machine (idle/wander → chase the nearest hero → telegraphed windup → strike → recover; stagger on hit; fade and respawn at home), driven through the `MobWorld` interface the scene passes in (`strike` for melee, `shoot` for projectiles); pacing is per kind (`windup`/`recover`/`stagger` via `mobTimings`, so tough kinds shrug off stun and quick ones swing fast), and a kind with a `shot` is a ranged attacker (stops at range, backs off when crowded, telegraphs with the cast pose, then fires a slow `foeBolt` the scene flies and tests against the players); on a co-op guest the same class is only a view of the host's state (`setRemote` also plays its windup and hurt poses). `effects.ts`: transient world visuals (slash arc, bolt, floating `BitmapText` numbers) owned by an `Effects` list. `ParticleEffect.ts`: draws a data-defined particle effect (`ParticleContainer`, one per emitter) as an `Effect`; spawn with `particleEffect('name', x, y, { dir })`. Character theme: a boy stranded outside time.
- **Characters (paper-doll)** — `src/sprites/doll.ts` (Pixi-free) defines the doll sheet and outfits: every layer is packed by `tools/sprites` onto one 832x1600 layout (64px frames for walk/idle/cast/hurt/shoot, 128px frames for the weapon swing; rows up/left/down/right) so layers stack frame-for-frame. An `Outfit` is a part id per slot (`body, head, eyes, hair, beard, torso, legs, feet, hands, cape, headwear, weapon, shield`); `outfitLayers` sorts all layers by `z` (LPC's zPos: lower is behind, so a cape or sword can sit both behind and in front of the body). `src/sprites/Wardrobe.ts` loads parts as plain `<img>` elements (not Pixi textures: they are only drawn onto a canvas, and the browser may drop an unused image's decoded pixels, where an `ImageBitmap` would pin 5 MB per layer) and composes an outfit into one `Texture` on a canvas; mobs of a kind and equal NPC looks share a sheet. Sheets are reference-counted (`sprites/sheetCache.ts`, `RefCache`): every `wardrobe.sheet()` takes a reference that the `Character` holding it gives back on `setSheet` or `destroy` (`releaseSheet`), and a sheet nobody uses is kept as one of `SPARE_SHEETS` (4) spares, then destroyed, so gear changes in a long co-op game don't pile up 10 MB sheets. Only hand a sheet to a `Character` (or release it yourself). **Hero gear** (`systems/items.ts`) has ten slots (`GEAR_SLOTS` in `combat.ts`: `weapon`, `offhand`, `head`, `chest`, `legs`, `feet`, `cape`, `tool`, `bag`, `charm`; only the weapon is always filled; a charm is a talisman with no doll art). Items can also carry buffs: `speed` (% faster, `speedFactor`), `magic`, `regen`/`mpRegen` (per second), `xpBonus`/`goldBonus` (%), summed over everything worn in `combat.ts` and applied in `Simulation` (host/solo only; a guest just sees the result); `rare: true` marks quest rewards (gold slot colour, never in a shop). Add a buff by adding the field to `Item`, a helper in `combat.ts`, `buffTexts` in `hud/itemText.ts` and the rule where it applies and each item carries a `look` (doll slots it sets; the off-hand sets `shield`, so a shield or a mirrored dagger `shield.dagger_left` goes there). `attack`/`defense` of everything worn add up (`gearAttack`/`gearDefense`). `systems/looks.ts` lays every piece over `HERO_BASE` (`heroOutfit`), and `OverworldScene.equip(item)` recomposes the sprite. **Bows** are weapons with a `ranged` field (`speed`, `range`, `cooldown`): the action key plays the `shoot` pose, and the arrow leaves at the release frame (`SHOOT_RELEASE_MS`, via `Player.pendingShot`; a hit while drawing spoils it) along the hero's aim (`arrowEffect`); guests see `draw` and `arrow` events. LPC bows are only drawn in the shoot/hurt poses, so the bow appears while the hero draws it. **Co-op players** each have their own base clothes, ring colour and name (`PLAYER_BASES`, `PLAYER_COLORS`, `playerName`, `playerOutfit(slot, hero)` in `systems/looks.ts`; slot 0 is the host's hero, `heroOutfit`); a guest's one-shot poses (slash/cast/hurt/shoot) are played from the world events, so `Player`'s `body` needs no extra net state. **NPC looks** are `NPC_LOOKS`; **mob looks** are `MobKind.look`. `assets.ts` preloads every part any hero outfit (`allPlayerOutfits`: each item on each base look), NPC or mob kind uses (about 1 MB at boot: every tool writes PNGs through `encodePng` in `tools/map/image.ts`, which stores art of 256 colours or fewer as an indexed PNG, 8x smaller than RGBA); `systems/*` and a test (`tools/sprites/parts.test.ts`) fail on an unknown part, a part in the wrong slot, or a missing body/head.
  - **Part catalog** `sprites/parts.ts` is the source of truth for which LPC art ships (id = `<slot>.<name>` → generator item, body type, colour). `npm run sprites -- build` (with `LPC_DIR` = a clone of the generator) recolours with the generator's palettes, packs each layer to `public/sprites/lpc/<id>.<n>.png` and writes `parts.json` (id → layers with z) and `credits.csv` (per-file authors/licences). Never hand-edit those; commit them with the catalog. See the `add-sprite-part` skill.
  - **Limits**: only weapons whose swing is 128px frames fit (arming sword family, dagger); LPC "oversize" swings (longsword, mace, axe, ...) are 192px and not packed yet. Items missing idle art use the first walk frame; weapons and shields vanish during the cast pose (no art). Body-shaped garments (tunic, pants, boots, armor) differ per body type, so a female NPC needs `f_` parts; hair, hats and weapons are shared. Items with several recolour groups other than skin+eyes are not supported by the packer.
- **Co-op (up to 4 players, peer-to-peer gameplay)** — `src/net/`. Settings → **Online** tab: **Host → Create Game** shows a short code like `mighty-apples` (also a `#join=` link) and a roster of the four seats; up to three friends **Join** with the code; the host taps **Start Game** (or the last seat fills) and the code stops working. `PeerLink.ts` is one `RTCPeerConnection` + data channel, one per friend (a star: every friend connects to the host, never to each other) (`{ ordered: false, maxRetransmits: 0 }`, public STUN only, so no TURN for gameplay: two strict NATs can't connect). An offer/answer is a full session description with every ICE candidate (gathering waits for `complete`, capped at 10 s), deflated by `CompressionStream` and base64url-encoded (`signal.ts`). **Setting up a game goes through the matchmaking relay** (`relay/`, a Cloudflare Worker). An offer fits exactly one connection, so the host prepares one offer per seat up front and `relayClient.ts` stores them under the code; each friend who types the code is given the next free seat and its offer, answers it, and the host long-polls for answers (cursor-based), so each exchange takes about a second; `roomCode.ts` (shared with the Worker) is the two-word code format; `relayApi.ts` is the wire format; `relayConfig.ts` holds the deployed relay's URL (`DEPLOYED_RELAY_URL`, or `VITE_RELAY_URL` at build time; empty means online play is shown as not set up). Gameplay never goes through the relay. `session.ts` is the state shared by the menu and the game loop (`mode`, `status`, `role`, `slot`, `connectedSlots()`, `roster()`, the host's `code`/`lobbyOpen`, parked incoming messages, version handshake) and runs `createGame()` / `joinGame()` / `startGame()`: the host keeps a `Seat` per friend (waiting, joining, connected), refills a seat with a fresh offer when its friend leaves while the code is open, ends the game when the last friend leaves after Start, and a friend's drop never affects the others; the host leaving ends it for everyone (no host migration). `looks.ts` gives each player number its own clothes, ring colour and name; the scene tags everyone "P1"–"P4" in co-op. `protocol.ts` defines the messages and validates everything from the peer (`parseMessage` never throws); `mobWire.ts` flattens a `MobView` (systems/combat.ts) to the tuple a snapshot carries and back (a mob exposes a plain `MobView`; the wire format is net's: `net/` imports only `core/` and `systems/`, and `entities/` never imports `net/`); `interp.ts` glides snapshots. Roles: **host** runs the normal simulation plus a `Player` per friend driven by that friend's input (`reconcileGuests` keeps them in step with the session's connected seats), and sends each friend a snapshot at 25 Hz (the players in that friend's zone, that friend's own stats, the items on the ground (listed when they change and once a second; absent means unchanged), the mobs *near that friend* (`net/feed.ts`, `MobFeed`, one per friend and zone: within the view radius the friend reports in its input message (`vr`) plus a margin; a mob whose state has not changed is repeated only every 0.24 s, and its timer is 0 outside windup/recover/dead so a still mob really is unchanged) and the one-shot events near that friend (`eventInView`: the view radius plus the margin, plus how far a shot can fly) that they have not acknowledged, as flat tuples (`EventWire`, `encodeEvent`/`decodeEvent`, about 25 B each) and only as many as fit the room the rest leaves under `SNAP_BUDGET` (1100 characters, `fitEvents`, newest first); about 0.2 KB quiet and under 1.2 KB in a big fight with four players: a message over about 1.2 KB is split in transit and, on this lossy channel, losing any piece loses all of it, so keep it small; `protocol.test.ts` checks a busy snapshot with a full ground list); the guest merges two snapshots that arrive in one frame (`mergeSnapshots`: a snapshot leaves out unchanged mobs and ground, so the older one's still count); **client** runs no simulation: it sends held keys at 30 Hz and renders snapshots (`Mob.setRemote`/`updateRemote`), with no prediction. The channel is lossy, so inputs are *state* (keys held) plus running counters for presses, and one-shot visuals (damage numbers, slashes, bolts; an enemy's shot is a `bolt` event with a `color`, drawn but never simulated on the guest) ride in snapshots with ids and are shown once; the guest's input messages carry the newest id it has shown (`ack`), so the host stops repeating an event once it has arrived (it still expires after 0.6 s if no ack comes). Events caused by a player carry that player's number (`p`) so the guest plays the pose on the right character. Online play never pauses the world (menu and dialogs are local overlays); kills share XP between every player; a friend's solo hero is restored when they leave, and the game returns to solo when nobody is connected. - **Zones and doors (several maps, one world)** — a *zone* is one `MapData`: the ten open-air biomes of the world (`greenwood`, the start, `town`, `eastwood`, `desert`, `beach`, `undead`, `jungle`, `wetlands`, `marsh`, `frostlands`; see Map pipeline → World) and a room per shop (`shop_smithy`, `shop_armory`, `shop_apothecary`, `shop_ranger`, `shop_wizard`). `MapData.doors` (`z.door(col, row, w, toZone, toCol, toRow)`) are cells that take a player to another zone; `MapData.indoor` (`z.indoor()`) rooms get no weather, ambient or overview map. Pixi-free geometry in `map/doors.ts` (`doorAt`, `doorsNear`, `arrivalFacing`, tested). `scenes/ZoneState.ts` bundles everything per loaded zone (`MapView`, `Collision`, `Camera`, `Effects`, mobs, chests, shopkeepers, ground items, `heroBodies`); `OverworldScene` keeps `zones` (by name) and each `Player` has a `zone`. **The scene works in one zone at a time through `this.zone`**: outside the per-zone loops it is the local player's zone (`this.view`, the only one drawn, swapped onto `stage` by `showZone`, under a `ZoneTransition`), and `inZone(z, fn)` points it at another zone for a moment so one set of rules (`mobs`, `chests`, `players()`, `bodies()`...) serves all of them; `players()` is the players in the current zone, `everyone()` all of them. **Efficiency**: only zones with a player in them are simulated (`occupiedZones`), so a shop nobody is in, or a zone everyone has left, costs nothing; zones load on demand (`ensureZone` via `assets.loadZone`) and `prefetchDoors` starts loading the zone behind any door within 5 cells of a player (host: of every player; guest: of the local one) so stepping through is instant, and a door whose zone is not ready yet simply waits a frame. **Memory stays bounded**: `Zones.retire` unloads a zone nobody has been in or near a door into for `RETIRE_AFTER` (20 s) (never the start zone, which a defeat wakes you in): `ZoneState.dispose` frees its map, mobs and characters (their sheets go back to the wardrobe), `assets.unloadZone` frees its map and every tileset no other loaded zone uses (tilesets are reference-counted), and what must last is kept in `Arena.memory` (`ZoneMemory`: opened chests and the items on the ground, with their ages; `Ground.stash`/`restore` include it) and given back by `Zones.add` when it loads again (its mobs start afresh). A guest counts only itself. A zone that is loaded but not shown has its map sprites freed (`MapView.release`). **Travel** (`travel`): host/solo move the player (`doorAt` each frame, not while reading a dialog/shop), set their zone, place them at the door's `to` cell facing away from the door, give `ARRIVE_GRACE` immunity (`Player.grace`, 1.8 s, longer than the transition because the world runs behind it; silent, unlike the blinking `invuln` after a hit, and `Player.safe` is either) and play a **door transition** for the local player (`beginTrip`): `map/transition.ts` (Pixi-free, tested) picks an **iris** (a black ring, drawn as a thick stroke rather than a rectangle with a hole cut in it: a `cut()` hole that crosses the rectangle's edge, as a circle larger than the screen does, draws solid black and flashes the screen; it closes on the hero in the old view, then opens around them in the new one) when either zone is `indoor` (shop rooms; caves should be `indoor` too) or the trip does not start near a map edge (waking at the spawn after a defeat always irises), and a **slide** (the old view pushed off toward the edge walked off while the new zone slides in behind it, Zelda-style) between two open-air zones when the player leaves within `EDGE_REACH` (8 cells) of an edge, or through a door that names its direction (`DoorSpawn.dir`: every gap between two biomes does, since a biome's border can be anywhere in its map; `Zones.beginTrip` looks for that door around the local player, so a guest slides the same way). **A crossing happens at the edge of the screen, in one slide, like a Zelda screen change**: `map/edges.ts` (`edgeLimits`, Pixi-free, tested) first holds the camera inside the zone's own cells everywhere (`zoneRegion`: the span of non-`beyond` cells per row and column, tightened over the rows the view can show and averaged, so the neighbour's margin is never on screen and the player walks to the screen's edge at a wall as well as at a gap; the player is always kept `KEEP` inside the view; limits closer together than the view is wide, as in a neck of a zone, centre the view between them (`limitOffset`) instead of favouring one side), and stops the camera at the border while the player is level with a gap (within `HOLD_CELLS` along the border, easing off over `FADE_CELLS` so the camera never jumps), so they walk off-centre to the very edge of the screen and step on the door; the one slide then moves exactly one screen (the old picture ends at the border and the new view, pinned the same way by the other zone's doors, starts from it), and across the border the hero keeps the screen position they had along it (`ZoneTransition.align`: the new view starts offset sideways so the hero lines up, and eases to its own framing as it settles), and they arrive `ARRIVE` (1) cell inside the new zone, at its edge, where the camera frees itself as they walk in. `ZoneState.follow` applies the limits (all camera moves go through it); `Camera.shift` applies the slide without disturbing the view used for chunks and weather. `PREFETCH_REACH` is 14 cells so the neighbour is loaded before the player reaches the edge. `entities/ZoneTransition.ts` draws it over the stage (the scene's `root` is `top` = stage + transition): the old view is a still picture taken with `renderer.generateTexture` just before the swap (in a slide without the hero, who slides in with the new zone, and without the weather, which stays fixed on screen); the local player stands still and takes no door while it plays. Purely visual: the simulation moved the player at once, so it is the same for solo, host and guest. **Co-op**: players can be in different zones at once. The host simulates every occupied zone and sends each friend a snapshot of *their* zone only (`SnapMsg.zone`, plus `away`: the slots of players in other zones, so they are not mistaken for having left; mobs, chests and events are that zone's; friends in the same zone share one built snapshot per tick). A guest that finds itself in a new zone (`followToZone`) loads it if needed (the iris closes on the old zone and holds shut meanwhile), plays the same transition, moves its own body there and re-places the others from the list. Events carry their zone (`emit`). `tools/map/check.ts` `checkDoors` (run by `npm run map -- check`) fails a door to a missing zone, one arriving on a wall or another door, or with no door back. Interiors are built by `tools/map/interiors.ts` (`shopInterior`) from `interior.png` (floor, wall, doormat, counter, shelves, signs), drawn by `tools/map/interior.ts` (part of `npm run tilesets`) in the shop buildings' palette; the town's door cells are `SHOP_DOORS` in `maps/town.ts` (world cells), which the shop rooms read through `shopExit` (in the town's own cells). `checkDoors` runs over the biomes too. **`checkCrossings` (also in `npm run map -- check`, with `tools/map/walk.ts`) walks the real collision box through every directional door: the arrival fits, the way ahead stays open for 6 cells (no bush in the doorway) and a body can walk 30 cells on (or reach the spawn), so no crossing drops a player into a pocket.**

The ice tiles are painted (cracks, glints) by `tools/map/recolor.ts` into the empty corner of `frost_ground.png`; the lake's ring cells keep the snow surface, so only the inner fill is slippery.
- **Weather** — each biome has its own (`systems/weather.ts`, Pixi-free, tested): a zone's `MapData.climate` (a key of `CLIMATES`, set by `defineBiome({ climate })`; rooms have none) says which precipitation can fall there: `temperate` (greenwood, eastwood, town: rain, storm), `coast` (beach: rain, storm, windier), `desert` (sandstorms only), `jungle` (heavy rain and storms), `swamp` (wetlands, marsh: rain), `undead` (ash, storms) and `frost` (snow, blizzards; snow falls nowhere else). A `Weather` (one per `ZoneState`) keeps **precipitation** (`Precip`: rain, storm, snow, blizzard, sand, ash, or none) and **wind** (`windLevel`: none, a breeze or a gale, plus the precipitation's own `LEAN`; direction ±1) separately: `CLEAR_SHARE` (80%) of the time there is neither; otherwise it is precipitation alone, wind alone, or both. Spells last 90-180 s, clear or not, so the time share matches, and ease in and out over 6 s. Only zones with a player in them are advanced (`Simulation.weather`, in the per-zone loop; a zone that is unloaded starts afresh, and a new `Weather` starts at a random point of a spell), and lightning is rolled there too (`Weather.strikeDue`, only in a built-up storm; the bolt lands around a random player *in that zone*: a `lightning` world event, and a player within `LIGHTNING_RADIUS` takes 35% of their max HP). `entities/WeatherLayer.ts` only draws a `Weather` (a haze for some, a pooled field of streaks/flakes/grains/ash in one `ParticleContainer`, gust streaks for wind alone, a flash and a seeded jagged bolt); the layer is part of its zone, so in a door slide each biome's sky slides with it. Wind blows leaves (`Ambient.wind`). Weather is a backdrop and must stay cheap: no full-screen frame or heavy dimming (a full-screen haze layer is the costliest part; snow has none), and drops are placed by a low-discrepancy sequence (`Drop.u/v`) so they spread evenly instead of clumping. **Co-op**: the host rolls every occupied zone's weather and sends each friend *their zone's* in the snapshot (`SnapMsg.w`: `[precip index + 1 or 0, wind %, intensity %, 1 if it blows right]`; `Weather.snapshot`/`setRemote`); a guest never rolls its own. Dev/playtest: `scenes.current.setWeather('rain', 0.85)` forces weather in the zone you are in (`setWeather(null, 0.35)` is a breeze alone).
- **Ambient life**: `src/entities/ambient.ts` is passive background animation driven by body movement and map metadata (no hooks into collision): footprints that alternate feet and fade within 2-3 s, only on soft terrain (`PRINTS`: `sand`, `snow`, and `puddle` once a puddle ground exists; hero and mobs; pooled, capped at 96), and leaves that drop when the hero moves behind a canopy (a `tree`/`bush`-tagged object drawn over the hero) or swings at one (`Ambient.shake`, called from `OverworldScene.attack`). Leaf colours follow the canopy's sheet name (`trees_green/frost/dry/jungle/dead/swamp.png`, `PALETTES`). It parents everything to `world.layer`. To add an effect, keep it pooled and capped, and key it off `surface`/`tag`/`level` rather than coordinates.
- **`src/map/`** — `types.ts` (`MapData`, `parseMap`) and `MapView.ts`: a render group with a `ground` layer and a y-sorted `layer` holding map objects (cullable via `CullerPlugin`) plus everything the scene adds (characters, effects). **It streams**: the map is cut into `CHUNK` (16) cell chunks (`map/chunks.ts`, Pixi-free, tested) and `update(view)`, called every frame after the camera moves (and by `Zones.show`), builds the chunks round the view (each chunk's ground its own render group, its objects added to `layer`) and frees the ones left two chunks behind, so a big zone costs about what a small one does; only the map data stays. Add entities to `world.layer`, never to the `MapView` itself, and don't rely on a map object's sprite existing.
- **`src/assets.ts`** — all loading goes through the Pixi `Assets` manifest: the sprite part manifest (the part layers used at boot are loaded by `Wardrobe.load` as images, see Characters) and per zone `loadZone(name)`: the map JSON, read by `parseMap`, then the tilesets it names, each loaded once under `tileset:<file>` and counted per zone using it, so `unloadZone(zone)` frees exactly the sheets no other loaded zone needs. Every URL under `public/` the game fetches (maps, tilesets, `parts.json`, part layers) carries `?v=<hash of that file>` from `virtual:asset-versions` (`tools/assetVersions.ts`, a Vite plugin that hashes `public/maps`, `public/tilesets` and `public/sprites/lpc` at build time; empty in the dev server), so a deploy never pairs new code with a cached old map or sheet, and a file that did not change keeps its URL and stays cached. A new folder of fetched files goes in `VERSIONED_DIRS`. `__BUILD_ID__` is only the co-op version handshake. Don't call `Assets.load` ad hoc elsewhere (the `Wardrobe` is the one sanctioned exception, for sprite layers, which it loads as `<img>` elements).
- **HTML overlays** (`src/hud/`; markup in `index.html`, styles in `src/ui.css`): `Hud.ts` (HP/MP bars), `Dialog.ts` (`#dialog`; tapping it advances; `layout()` keeps it clear of the touch controls), `Menu.ts` (pause menu: Status / Inventory / Controls / Online, plus Trade while online, with Credits as a lone tab in the bottom-left corner; the Online tab is `Multiplayer.ts`, which only drives the `Session`) and `MapOverlay.ts` (the co-op map, below) and `Loading.ts` are DOM rather than Pixi so text stays sharp on phones and can use safe-area insets.
- **UI look**: Lamoot's RPG GUI kit (CC-BY 3.0, credited in CREDITS.md). `tools/ui/cut-gui.ts` cuts pieces from `art/rpg_gui_v1/RPG_GUI_v1.png` into `src/ui/` (bundled by Vite via `ui.css`): gold frames used as `border-image` on `.panel` (`.thin` variant), `.wood`/`.paper` backgrounds, plank tabs, square buttons, D-pad arrows. Fonts: Cinzel (titles) and Crimson Text (body) from Fontsource. Reuse these classes for new UI rather than inventing new styles.
- **Touch controls**: `src/core/touch.ts` wires the on-screen D-pad (shown when the primary pointer is a finger or after a touch, hidden again on any physical key press) into `input` as virtual arrow-key presses (`input.setVirtual`), and makes every `[data-key]` element (A = KeyJ, B = KeyK, the ☰ and menu ✕ = Escape) press that key while held, so game code only ever reads key codes. To add a button, add a `data-key` element.
- **Map pipeline** — maps are built by agents from code, not painted: **use the `build-zone` skill** (`.claude/skills/build-zone/SKILL.md`) for any map change.
  - `maps/<zone>.ts` (source of truth) uses the `Zone` builder (`tools/map/zone.ts`: `fill`, `patch`, `forest`, `prop`, `stamp`, `plateau`, `block`/`unblock`, `spawn`/`npc`/`mob`) with named assets from `tools/map/catalog.ts`. `npm run map -- build` compiles it to `public/maps/<zone>.json`, renders `maps/out/<zone>.png` + `.debug.png` (gitignored), and runs `tools/map/check.ts`. Never hand-edit the JSON; `npm run build` fails if it's stale or a check errors.
  - The JSON is a packed `MapData` (`PackedMap` v3 in `src/map/types.ts`, written by `tools/map/encode.ts`: ground cells index a palette of shared layer stacks, objects are `[part, px, py]` triples into a parts table; `parseMap` unpacks it, and still reads the older v2). `MapData`: 32px ground cells referencing 32x32 regions of tileset sheets (a cell may stack several `[sheet, x, y]` layers, bottom first: terrain edges drawn over the ground; `MapView` and the previews draw them in order), free-placed objects (y-sorted by bottom edge, or by an explicit `z` for flat art like cliffs; each can carry a `tag` such as tree/bush/rock/cliff), a collision cell list, per-cell terrain metadata (`surface` names like grass/sand/snow, `level` height, `ramps` = stairs) for game systems, spawn/NPC cells and mob spawns. The game reads collision, surface (footprints) and tags (leaf fall); `level`/`ramps` are for height-aware movement (see Roadmap). `MapView` renders it in the game; `tools/map/image.ts` renders the same way in Node for previews. Tilesets live in `public/tilesets/`; all art is cut on the 32px grid.
  - **Cliffs**: `z.plateau(rect, {kind, stairs})` builds a raised plateau from the Avalon blob on `Cliff_tileset.png` (cut along its grass hole so it scales to any size >= 4x4; measurements in `CLIFF`, `tools/map/catalog.ts`). `rect` is the walkable top; the rim ring and two face rows around it block; stairs are the only way up and become `ramps`. `kind` picks `grass`/`frost`/`dry` (`frost_cliffs.png`, `dry_cliffs.png`, derived in `recolor.ts`). The top is always the ground its rim is drawn with (`TOP_GROUND` in `zone.ts`: grass, snow, sand): `plateau` fills it and no terrain shows on it, painted before or after (a mesa in the desert's red dirt used to show a red middle inside a sand rim). The art is flat ground-level (`z` below all entities), so the hero draws over it. `check.ts` fails if two open cells of different level touch without stairs (a gap in a rim). `Extra_Unfinished4.png` (stone wall, door, brown drop-off) and `graphics-tiles-waterflow.png` (animated water) are still uncatalogued.
  - Collision for props is derived from their art (cells covered by the bottom `solid.band` px of the sprite), forests block their rect, so collision tracks the visuals. The tilesets have no foliage edge tiles — all vegetation is prefabs, and trees are cut from the LPC trees pack (see Trees and bushes).
  - **Terrain (autotiled ground)**: `z.paint(terrain, rects)` paints a terrain on cell *corners* from the LPC terrain atlas (`public/tilesets/lpc_terrain.png`, "Tiled Terrains" from OpenGameArt, source + Tiled tileset in `art/lpc_terrain/`; `tools/map/terrain.ts` reads which tile has which corners from `Terrain.tsx`), so any shape blends with soft edges and inner corners (dirt roads, sand, mud, ash, swamp water, ponds, ice, lava, pits...). Terrains stack over the cell's `fill` in `TERRAINS` order; the opaque `coast`/`snowCoast` bring their own sea. The atlas also gives full-cell grounds (`sea`, `cobble`, `flagstone`, `crackedStone`) and props (sandstone/basalt boulders, a standing stone, reeds, lily pads). `blob`, `pond`, `trail` and `reedsAt` in `tools/map/helpers.ts` make organic patches, ponds, winding trails and bank-side reeds; `tools/map/noise.ts` has the noise, `smoothMask` and `distanceField` that shape pools and ground edges. **`murk`** is swamp water: the atlas's soft-banked pond recoloured olive (`lpc_swamp.png`, `SWAMP_SHEET`, made by `recolor.ts`; a terrain may name its own `sheet`). The atlas's `Sewer Water` tile is rectilinear (a dungeon sewer) and is not used for swamps. **Reeds** (`reedBed`, `reedStalks`) are bank plants: put them on the land beside water, never in it (the atlas draws a water-edge strip under them, which is not used). The marsh keeps them two cells clear of its causeways, and their two foot rows block like a trunk's.
  - **Trees and bushes** come from the LPC trees pack (`art/lpc_trees/`, CC-BY-SA, see CREDITS.md), not the Avalon sheet. `tools/map/treePicks.ts` lists the picked sprites (rects that enclose one sprite), `tools/map/trees.ts` (part of `npm run tilesets`) cuts each out by its shape (keeping its translucent baked shadow), packs them into `public/tilesets/trees_<green|dry|jungle|dead|frost|swamp>.png` (frost and swamp recolour the green sheet) and writes `tools/map/treeAtlas.ts` (generated, never hand-edit). Every kind has six trees `treeA`..`treeF` (`frostTreeA`.., `dryTree..`, `jungleTree..`, `deadTree..`, `swampTree..`) and two bushes (`bush`, `bushSmall`; `frostBush`...); `TREES`, `FROST_TREES`, `DRY_TREES`, `JUNGLE_TREES`, `DEAD_TREES`, `SWAMP_TREES` list them for groves, walls and `scatter`. Collision: the bottom 75% of a sprite (`SOLID_SHARE`), the crown above it is walk-behind; `isArt` ignores translucent pixels so shadows never block. The leaf-fall (`entities/ambient.ts`) keys off the `tree`/`bush` tag and the sheet name (`trees_frost.png` → frost leaves), so a new kind needs a `PALETTES` key in its file name. To add or swap a tree, edit `treePicks.ts`, run `npm run tilesets`, then `npm run map -- build`.
  - **Recoloured sheets**: the Avalon pack only has grass/sand/water/stone, so snow and ice are *derived* sheets (`frost_ground.png`, `frost_objects.png` (blue-grey rocks), `ground_plus.png`) generated by `tools/map/recolor.ts` (`npm run tilesets`, outputs committed). Same coordinates as the originals, so catalog entries just point at another sheet; each has its own baked shadow colour (`SHADOWS`).
  - **World (the biomes)**: `maps/world.ts` lays the open-air world out after the hand-drawn map, one character per 10x10-cell square (34 x 23 squares = 340 x 230 cells), and lists the **gaps** between biomes. The borders don't follow the squares: `carve` (tools/map/world.ts) pushes each cell's lookup about with smooth noise (`wobble`, default 0.7 squares; `seed`), smooths away spikes and gives stray islands to their neighbour, so borders look carved, but runs them straight across every gap. Each biome is a `maps/<name>.ts` that default-exports `defineBiome({ name, climate, walls: { trees, fillers }, worldEdge?, build })` (`climate`: its weather, see Weather) and builds in *world* cells, placed in squares through `units(square)` (`at`, `area`) so the content scales with the layout. `buildWorld` (run by `npm run map`) walls every biome in along every border and the world's edge with `WALL` (3, a round band) cells of its own `woods`, cuts a 3-wide corridor through both walls at each gap (and keeps the way just past it open) with a door on each side leading straight across (`dir` set, arriving `ARRIVE` cells in), runs every spec, composes them into one world (`Zone.compose`: each cell from its owner; a see-through terrain fades across a border) and cuts each biome's map from it: its own cells plus `MARGIN` (14) cells of its neighbours, blocked (surface `beyond`) and **not drawn in the game** (`MapView` skips their ground and the objects standing in them, and the stage is black, so outside the zone is pitch black; the camera also never shows them, see `edgeLimits`; the previews in `tools/map/image.ts` still draw them). Pockets of open ground nobody can reach from the spawn are sealed. **Edges are never straight**: a wall's inner edge swells by up to `RAGGED` cells with noise on top of its `WALL` core (`World.wall`, from `World.borderDistance`, the distance of each cell to the nearest other biome); `z.ground(terrain)` lays a biome's ground terrain over its own cells but stops `inset` cells short of the borders (default 3 to 7, wandering), so the grounds on either side of a border never meet in a straight line (use it instead of `z.paint(terrain, z.bounds)`); pass `inset: [1, 2]` so the edge lies under the walls rather than leaving a ring of grass inside them (the Barrow Lands' ash). **Jarring ground fails the build**: `tools/map/ground.ts` (`groundReport`, run by `checkMap` on every open-air map, tested in `check.test.ts`) measures the floor as it is drawn (ground layers plus cliff art, Lab colour): a *hard seam* is a colour jump right on a cell boundary (`SEAM_STEP`; autotiled edges change colour inside the tile, so they pass; a fill against a fill, a paved rect, a plateau top unlike its rim, the sea against grass do not), and a *clash* is one surface in two shades further apart than `CLASH_DE` within two cells (a deep green over a pale grass). Seams under props, the edge of cliff art on open ground and the drawn banks of ponds, bogs, lava, pits and ice are exempt. Paved spots use `z.patch('stone', rect)` (its own grassy edge), not a `fill` blob; the desert and beach lay soft `sand` terrain over their base so they fade across borders; `redDirt` is its own surface (`clay`). **A biome's ground is a palette of at most two**: two grounds may share a biome if their colours are close and the edge between them is soft (an autotiled terrain edge, a shape from `blob`/`z.ground`, never a bare rect or a cell-stepped line). The LPC `meadow`/`darkGrass` are too far from the Avalon `grass` fill to pair with it, so the green biomes use `grass` alone for now (the cliff art's grass, so plateaus match: a plateau's top must be the ground it stands on); a palette-matched second grass would be a terrain recoloured to sit beside `grass` (`recolor.ts`, as `murk` is); a `grove` never grows onto a road (cells kept clear, plus one of verge) and `scatter` keeps a tall prop's canopy rows off a road too. Maps include `MARGIN` (22) cells of the neighbours, more than half of a 1280 px wide view. **`checkSeams` (tools/map/check.ts, run by `npm run map -- check` and the zone test) enforces that borders match**: along every border both sides are blocked, or both are doors straight across to each other, and nothing is open on the world's edge. The beach sets `worldEdge: false` and closes the north with the sea. **Woods** (`z.grove(area)`, and the walls) are any shape: trees standing wholly inside it on a staggered lattice, then fillers for the corners, and its cells block only where that art covers them (`SOFT_COVER`; the row along a border always), so the edge of a wood is as walkable as it looks. **No invisible walls**: a wall plants 55% of its lattice (`WALL_DENSITY`), but every cell of its border row gets a tree, else a bush or rock (`woods`), so each side of every border shows its own line of trees; a border cell nothing fits over is marked `BARE_WALL` and fails `checkMap`. Shapes come from `blob` (a lobed outline), trails from `trail` (winding between nodes, straight into a gap's corridor `worldOf(layout).gap(a, b)`), points from `z.near(col, row)` (the nearest free cell, whatever the border did). A biome spec also gets `bounds`, `owns`, `keepClear` and a deterministic `scatter`. Plan against `npm run map -- layout <biome>`; keep a gap away from a bend of its border. Snow and sand both blend into grass.

## Working procedure (rapid dev mode)

The project is in rapid development, and this is how every session (Claude or human) works until the maintainers say it has matured:

- **Push to `main` before the full test suite, then fix forward.** Do not wait for `npm run build` or `npm run test:e2e` (the e2e suite takes 10+ minutes) before pushing to `main`. Push, then run them, and if something fails, fix it in a follow-up push. The game is a static single-page site, so a bad push cannot take anyone's running copy offline; other developers getting current code quickly matters more than a gate. A failing check after a push is the next thing to fix, not a reason to revert unless it makes the game unplayable.
- **Merge `main` in first, and often.** Drift is the real cost: fetch and merge `origin/main` before starting work and again right before pushing, and resolve conflicts then rather than leaving them for a PR. Keep changes small and push them as soon as they are coherent. Prefer a fast-forward push to `main` when the branch already contains it.
- **Hooks enforce the merge rule** (`.claude/settings.json`, scripts in `.claude/hooks/`): at session start `sync-main.sh` fetches `origin/main` and merges it into your branch when that is clean (it reports, and leaves the tree alone, if it conflicts or you have uncommitted changes); when a session ends `check-main.sh` blocks once if your branch has commits that are behind `origin/main`, telling you to merge now. They do nothing offline, on `main`, or on a detached HEAD.
- **Still cheap and worth doing before a push**: `npm run typecheck` and the unit tests (`npm run test`, seconds). If a quick check fails, fix it before pushing; do not skip it just because the full suite may be skipped.
- **Two things are not covered by "it cannot go offline"**: the matchmaking relay (`relay/`) is a live Cloudflare Worker that redeploys from `main`, and the game and relay deploy a minute or two apart. A change to `relay/` or to the relay API (`src/net/relayApi.ts`) can break everyone's co-op setup, so test those first. A protocol change (`PROTOCOL_VERSION`) makes players on the old page unable to play with players on the new one until they reload; that is expected, but say so in the commit.
- Never commit secrets or private assets (the repo and site are public), whatever the pace.

## Conventions

- **Keep multiplayer in sync with single player.** Co-op is not an afterthought: whenever a feature touches gameplay state (stats, gold, pack, gear, shops, chests, combat, mobs, map objects, a new key or menu tab), decide how it behaves for the host and for a guest *in the same change*. The host owns every hero and all simulation; a guest only sends wishes (`do`, `tr`, input) and renders what it is told (`snap`, `pack`, `looks`, `trade`). If something is solo/host-only for now, say so in the UI (e.g. the guest's "kept by the host" note) and in this file. Anything new that a guest must see goes through `src/net/protocol.ts` (validated in `parseMessage`, version bumped, a `protocol.test.ts` case) and `session.ts`; anything new that needs a guest's input is a numbered/ackable command, not a raw event. Add unit tests for the pure rules and an `e2e/multiplayer.spec.ts` case when a flow spans two players. **When you change a single-player system, update the co-op bullets above (and the matching ones in the other direction) so this file always describes both.**

- TypeScript is strict plus `noUncheckedIndexedAccess` and `verbatimModuleSyntax` for game code (`tools/` indexes freely). Prefer a clear error over `!` when data can be missing; `!` is fine for DOM lookups that `index.html` guarantees.
- Prettier owns formatting (single quotes, width 120); ESLint is type-aware and bans floating promises.
- New rules/maths go in a Pixi-free module with a `*.test.ts` beside it.

## Deployment

The relay (`relay/`) deploys separately: Cloudflare builds and deploys it from `main` itself (no GitHub workflow); see `relay/README.md`. A relay change only reaches players once that build has finished, so wait for it before relying on a new API.

`.github/workflows/deploy.yml` builds and publishes `dist/` to GitHub Pages on every push to `main` (repo Settings → Pages → Source must be "GitHub Actions"). `vite.config.ts` sets `base: './'` so asset URLs work under the `/<repo>/` subpath — keep asset references relative (put static files in `public/` and don't use root-absolute `/...` paths).
