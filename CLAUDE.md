# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A top-down RPG built with PixiJS v8 + Vite + TypeScript. The repo and the deployed site are fully public, so never commit secrets or private assets. Deployed as a static site to GitHub Pages.

## Direction

The game is intended to become Zelda-like: real-time action combat, item collection, and progression (leveling skills, weapons/armor, magic). The code is split into scenes, systems and entities (below); next up are more zones with map transitions, items/inventory and more enemy kinds. Art, story and gameplay are iterated on incrementally.

## Commands

- `npm run dev` — Vite dev server with HMR (also exposes `window.__game` for playtest scripts, dev only)
- `npm run build` — typecheck, `map -- check`, `sprites -- check`, then production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run verify` — everything CI runs except the build and browser tests: lint, format check, typecheck, unit tests, map check, sprite check. **Run it before committing.**
- `npm run lint` / `npm run format` / `npm run format:check` — ESLint (type-aware) and Prettier (`.ts`/`.json`/`.yml`; CSS, HTML and Markdown are hand-formatted)
- `npm run test` — Vitest unit tests (`src/**/*.test.ts`, `tools/**/*.test.ts`)
- `npm run test:e2e` — Playwright smoke tests against the production build (set `PW_CHROMIUM` to a local Chromium, e.g. `/opt/pw-browsers/chromium-*/chrome-linux/chrome` in cloud sessions)
- `npm run typecheck` — typecheck only (game, `tools/`, `e2e/`, `relay/`)
- `npm run relay` — the matchmaking relay in memory on `http://localhost:8787` (use with `VITE_RELAY_URL=http://localhost:8787 npm run dev` to try online play locally)
- `npm run map -- build|check|render …` — zone specs → map JSON + previews + checks (see Map pipeline)
- `npm run sprites -- build|check|preview …` — LPC part catalog → packed layer sheets (see Characters). `build` needs a clone of the LPC generator (`LPC_DIR`); `check` (run by `verify` and `build`) does not

CI (`.github/workflows/ci.yml`) runs `verify`, `build` and the e2e tests on every pull request; the deploy workflow runs `verify` before publishing.

## PixiJS skills

Vendored in `.claude/skills/` (`.agents/` is a gitignored duplicate). **Before changing anything in `src/` that touches PixiJS, load the `pixijs` skill** and follow the sub-skill it routes to (application, assets, scene-*, ticker, performance, math). Only the sub-skills this game uses are vendored; for anything else the router falls back to the live docs (`https://pixijs.download/release/docs/llms.txt`), or re-add a skill with `npx skills add pixijs/pixijs-skills`. Project conventions that follow them: `TextureStyle.defaultOptions.scaleMode = 'nearest'` and `resolution: devicePixelRatio` + `autoDensity` are set once in `main.ts` (don't set scale modes per texture); dynamic in-world text uses `BitmapText` with the pre-installed `FloatText` font, not `Text`.

Other project skills: `build-zone` (any map change), `add-mob-kind` (new enemy), `add-sprite-part` (new hair/armor/weapon/monster part), `add-particle-effect` (new/retuned particle effect), `playtest` (run/screenshot the game in a browser).

## Architecture

Pixi-free logic (rules, collision, camera maths, map format) is kept separate from Pixi code so it is unit-tested without a browser; keep it that way.

- `src/main.ts` boots: creates the PixiJS `Application` (async `app.init`, wrapped in a `void` IIFE — avoid top-level await), registers the manifest, loads assets behind the loading overlay, creates the shared DOM UI (`Hud`, `Menu`, `Dialog`, touch controls) and starts a `SceneManager` with an `OverworldScene`.
- **`src/core/`** — engine plumbing. `Scene.ts`: the `Scene` interface (`root`, `enter`, `update(dt)`, `resize`, `exit`) and `SceneManager` (runs one scene from `app.ticker` with a clamped dt, forwards resizes, and always calls `input.endFrame()` after each update). `camera.ts`: integer zoom chosen from the window size and a follow/clamp offset (`pickZoom`, `followOffset` are pure). `input.ts`: module-level keyboard + mouse singleton (`isDown`, one-shot `wasPressed`; mouse buttons are `Mouse0/1/2` codes and count only when a real mouse presses the canvas; `isHeld`/`wasHit` are keyboard+mouse only, `isTouched`/`wasTouched` on-screen buttons only; `captureKey` hands the next key to the rebind UI; ignores keys typed into text fields, so pasting a code can't move the hero). `bindings.ts` (Pixi-free, tested): the rebindable controls, two slots per action (`up/down/left/right/attack/magic/inventory`; defaults WASD/arrows, attack = left click or Space, magic = right click or K, inventory = I), saved in localStorage; menu/map keys (Esc, Tab, M) are reserved. `controls.ts` joins them to `input` (`actionDown`/`actionPressed`; the on-screen buttons always work too). Game code asks about actions, never raw keys, for movement/attack/magic. The editor is `hud/Keybinds.ts` on the Controls tab, hidden while touch controls are active (no customizing on mobile). `touch.ts`: on-screen controls (below). `textures.ts`: `makeFrame` and `sheetGrid`, a per-sheet cache of frame textures.
- **`src/scenes/OverworldScene.ts`** — one zone: a `MapView` world, the hero, NPC and mobs, hero combat (melee hit circle, Time Bolt projectile for MP, invulnerability blink + knockback, HP/MP regen, defeat → respawn at spawn keeping XP). The action key talks when next to the NPC, otherwise attacks. Solo, a dialog freezes the world and the menu pauses it. New areas should be new scenes (or new zones loaded into this one), not more code in here. Each frame it reads `Session.role` (`solo`/`host`/`client`, see Co-op); combat is per `Player` (`entities/Player.ts`: body + hero + cooldowns), driven by a `Command` from the keyboard or the network. `local` is the player at this keyboard, `remotes` (by player number) everyone else; player 0 is the host, friends are 1 to 3.
- **`src/systems/`** — `combat.ts`: stats, gear, `MobKind`s/`MOB_KINDS` and the damage/XP/level-up rules (`newHero`, `rollDamage`, `gainXp`). Levelling is superlinear: `xpToNext(level) = round(20 * level^1.5)` and `levelGains(level)` (stat gains per level-up) steps up every 4 levels; mob XP is fixed per `MobKind`, so a new tougher kind is how higher levels stay meaningful. `particles.ts` (Pixi-free `Emitter` simulation with fixed pools) and `particleEffects.ts` (the effects, pure data; add one with the `add-particle-effect` skill). `collision.ts`: `Collision` (cell collision from the map plus body-vs-body blocking: characters block each other but can always move apart; per-axis `slide`).
- **`src/entities/`** — `Character.ts` renders the hero/NPCs/mobs from a composed *doll sheet* (below): looping idle/walk follow `animate(dt, moving)`, one-shot `play('slash'|'cast'|'hurt', ms?)` takes over until done, `setSheet()` swaps the look when gear changes. Its container origin is the *feet*, so collision and y-sorting (`zIndex = y`) use it directly. `Mob.ts`: enemy AI state machine (idle/wander → chase the nearest hero → telegraphed windup → strike → recover; stagger on hit; fade and respawn at home), driven through the `MobWorld` interface the scene passes in (`strike` for melee, `shoot` for projectiles); pacing is per kind (`windup`/`recover`/`stagger` via `mobTimings`, so tough kinds shrug off stun and quick ones swing fast), and a kind with a `shot` is a ranged attacker (stops at range, backs off when crowded, telegraphs with the cast pose, then fires a slow `foeBolt` the scene flies and tests against the players); on a co-op guest the same class is only a view of the host's state (`setRemote` also plays its windup and hurt poses). `effects.ts`: transient world visuals (slash arc, bolt, floating `BitmapText` numbers) owned by an `Effects` list. `ParticleEffect.ts`: draws a data-defined particle effect (`ParticleContainer`, one per emitter) as an `Effect`; spawn with `particleEffect('name', x, y, { dir })`. Character theme: a boy stranded outside time.
- **Characters (paper-doll)** — `src/sprites/doll.ts` (Pixi-free) defines the doll sheet and outfits: every layer is packed by `tools/sprites` onto one 832x1600 layout (64px frames for walk/idle/cast/hurt/shoot, 128px frames for the weapon swing; rows up/left/down/right) so layers stack frame-for-frame. An `Outfit` is a part id per slot (`body, head, eyes, hair, beard, torso, legs, feet, hands, cape, headwear, weapon, shield`); `outfitLayers` sorts all layers by `z` (LPC's zPos: lower is behind, so a cape or sword can sit both behind and in front of the body). `src/sprites/Wardrobe.ts` loads parts (through `Assets`) and composes an outfit into one cached `Texture` on a canvas; mobs of a kind and equal NPC looks share a sheet. **Hero gear** (`systems/items.ts`) has nine slots (`GEAR_SLOTS` in `combat.ts`: `weapon`, `offhand`, `head`, `chest`, `legs`, `feet`, `cape`, `tool`, `bag`; only the weapon is always filled) and each item carries a `look` (doll slots it sets; the off-hand sets `shield`, so a shield or a mirrored dagger `shield.dagger_left` goes there). `attack`/`defense` of everything worn add up (`gearAttack`/`gearDefense`). `systems/looks.ts` lays every piece over `HERO_BASE` (`heroOutfit`), and `OverworldScene.equip(item)` recomposes the sprite. **Bows** are weapons with a `ranged` field (`speed`, `range`, `cooldown`): the action key plays the `shoot` pose, and the arrow leaves at the release frame (`SHOOT_RELEASE_MS`, via `Player.pendingShot`; a hit while drawing spoils it) along the hero's aim (`arrowEffect`); guests see `draw` and `arrow` events. LPC bows are only drawn in the shoot/hurt poses, so the bow appears while the hero draws it. **Co-op players** each have their own base clothes, ring colour and name (`PLAYER_BASES`, `PLAYER_COLORS`, `playerName`, `playerOutfit(slot, hero)` in `systems/looks.ts`; slot 0 is the host's hero, `heroOutfit`); a guest's one-shot poses (slash/cast/hurt/shoot) are played from the world events, so `Player`'s `body` needs no extra net state. **NPC looks** are `NPC_LOOKS`; **mob looks** are `MobKind.look`. `assets.ts` preloads every part any hero outfit (`allPlayerOutfits`: each item on each base look), NPC or mob kind uses (~6 MB at boot); `systems/*` and a test (`tools/sprites/parts.test.ts`) fail on an unknown part, a part in the wrong slot, or a missing body/head.
  - **Part catalog** `sprites/parts.ts` is the source of truth for which LPC art ships (id = `<slot>.<name>` → generator item, body type, colour). `npm run sprites -- build` (with `LPC_DIR` = a clone of the generator) recolours with the generator's palettes, packs each layer to `public/sprites/lpc/<id>.<n>.png` and writes `parts.json` (id → layers with z) and `credits.csv` (per-file authors/licences). Never hand-edit those; commit them with the catalog. See the `add-sprite-part` skill.
  - **Limits**: only weapons whose swing is 128px frames fit (arming sword family, dagger); LPC "oversize" swings (longsword, mace, axe, ...) are 192px and not packed yet. Items missing idle art use the first walk frame; weapons and shields vanish during the cast pose (no art). Body-shaped garments (tunic, pants, boots, armor) differ per body type, so a female NPC needs `f_` parts; hair, hats and weapons are shared. Items with several recolour groups other than skin+eyes are not supported by the packer.
- **Co-op (up to 4 players, peer-to-peer gameplay)** — `src/net/`. Settings → **Online** tab: **Host → Create Game** shows a short code like `mighty-apples` (also a `#join=` link) and a roster of the four seats; up to three friends **Join** with the code; the host taps **Start Game** (or the last seat fills) and the code stops working. `PeerLink.ts` is one `RTCPeerConnection` + data channel, one per friend (a star: every friend connects to the host, never to each other) (`{ ordered: false, maxRetransmits: 0 }`, public STUN only, so no TURN for gameplay: two strict NATs can't connect). An offer/answer is a full session description with every ICE candidate (gathering waits for `complete`, capped at 10 s), deflated by `CompressionStream` and base64url-encoded (`signal.ts`). **Setting up a game goes through the matchmaking relay** (`relay/`, a Cloudflare Worker). An offer fits exactly one connection, so the host prepares one offer per seat up front and `relayClient.ts` stores them under the code; each friend who types the code is given the next free seat and its offer, answers it, and the host long-polls for answers (cursor-based), so each exchange takes about a second; `roomCode.ts` (shared with the Worker) is the two-word code format; `relayApi.ts` is the wire format; `relayConfig.ts` holds the deployed relay's URL (`DEPLOYED_RELAY_URL`, or `VITE_RELAY_URL` at build time; empty means online play is shown as not set up). Gameplay never goes through the relay. `session.ts` is the state shared by the menu and the game loop (`mode`, `status`, `role`, `slot`, `connectedSlots()`, `roster()`, the host's `code`/`lobbyOpen`, parked incoming messages, version handshake) and runs `createGame()` / `joinGame()` / `startGame()`: the host keeps a `Seat` per friend (waiting, joining, connected), refills a seat with a fresh offer when its friend leaves while the code is open, ends the game when the last friend leaves after Start, and a friend's drop never affects the others; the host leaving ends it for everyone (no host migration). `looks.ts` gives each player number its own clothes, ring colour and name; the scene tags everyone "P1"–"P4" in co-op. `protocol.ts` defines the messages and validates everything from the peer (`parseMessage` never throws); `interp.ts` glides snapshots. Roles: **host** runs the normal simulation plus a `Player` per friend driven by that friend's input (`reconcileGuests` keeps them in step with the session's connected seats), and sends each friend a snapshot at 25 Hz (every player, every mob, that friend's own stats, recent one-shot events; about 1.1 KB at most with four players and 19 mobs, near one network packet, so keep it small); **client** runs no simulation: it sends held keys at 30 Hz and renders snapshots (`Mob.setRemote`/`updateRemote`), with no prediction. The channel is lossy, so inputs are *state* (keys held) plus running counters for presses, and one-shot visuals (damage numbers, slashes, bolts; an enemy's shot is a `bolt` event with a `color`, drawn but never simulated on the guest) ride in several snapshots with ids and are shown once. Online play never pauses the world (menu and dialogs are local overlays); kills share XP between every player; a friend's solo hero is restored when they leave, and the game returns to solo when nobody is connected. Changing a message shape: bump `PROTOCOL_VERSION` (now 7; v6 added `do`, `pack` and `looks`, v7 added `tr` and `trade`). Tests: unit tests for the pure parts (`session.test.ts` drives the whole seat lifecycle with a fake link and relay); `e2e/multiplayer.spec.ts` connects up to five real browser contexts through a local copy of the relay (`tools/relay/dev-server.ts`, started by `playwright.config.ts` with the game built against it).
- **Player trading (co-op)** — `systems/trade.ts` (Pixi-free, tested): the host's `TradeBook` is the only authority. Players (the host included) send `TradeCommand`s (`ask`, `yes`/`no`, `offer` = item codes + gold, `ready` on/off, `cancel`); the book checks them against the real heroes. Flow: a player asks someone within `TRADE_START` (3 cells) from the **Trade tab** of the menu (shown only online, `Menu.setOnline`; each player is listed with a button that is disabled when too far); the other gets an Accept/Deny prompt (`#trade-request`; lapses after 30 s; two players asking each other counts as yes); then the shared window (`#trade`, `hud/Trade.ts`, a modal like the shop counter that freezes the hero) where each side offers pack items and gold; **any change to either offer clears both Accept marks**, and when both accept the swap happens atomically or not at all (goods and pack room are re-checked; a failure changes nothing and says why). The trade ends if players drift past `TRADE_KEEP` (5 cells), leave, or either cancels (Esc / the ✕ cancels an open trade). Only pack items can be offered (not worn gear). On the wire (`tr` guest→host, `trade` host→guest, `protocol.ts`) commands are numbered and the guest repeats every unacknowledged one until the host's `ack` covers it (the host takes only the next number), so the lossy channel can't drop a click; the host sends each friend their view/note when it changes and once a second; the gold/pack result then arrives through the normal `pack` message. `TradeUi.sync` draws from a `TradeView` every frame; `OverworldScene` (`syncTrade`, `tradeCommand`, `handleTradeSteps`, `sendTrade`) joins it to the book (host: direct; guest: queue + host view). The UI keeps a local draft of your offer while commands are unacknowledged.
- **Co-op map overlay** — `src/hud/MapOverlay.ts` (markup `#map-overlay` in `index.html`): while online (`Role` is `host`/`client`) the HUD shows an `M` button (`data-key="KeyM"`, so touch works) and the M key toggles a semi-transparent map of the whole zone with a pin for you and one per friend, each in that player's colour (it never takes pointer input; the world keeps running). The terrain pixels (one per cell from surface + collision) and the world→percent mapping are Pixi-free in `src/map/minimap.ts` (unit-tested); the image is painted once on a detached canvas and shown as an `<img>` so the page keeps a single `<canvas>` (the smoke tests rely on that). `OverworldScene` calls `setAvailable(online)` every frame, so leaving a game closes the map.
- **Relay (`relay/`, Cloudflare Worker + Durable Objects)** — one Durable Object per game code (`room.ts`: seats with one offer each; join takes the next free seat, a seat whose friend never answers is freed after 60 s; answer; cursor-based long-poll for the host; the host can reopen a seat, close the game to newcomers, or cancel; 10-minute expiry), a public router (`router.ts`: CORS to the game's origin, per-client rate limits, picking a free code, validating that only list words reach storage), `limiter.ts`, and `index.ts` (the only file that touches Cloudflare APIs). The logic is pure and runs unchanged in Node against an in-memory backend (`tools/relay/memory.ts`), which is what the tests (`tools/relay/*.test.ts`, including the real client against the real router) and the dev server use. Deployed by Cloudflare's own git integration (Workers Builds, root directory `relay`, set up in the Cloudflare dashboard, not in this repo), so a push to `main` that changes `relay/` redeploys it; it lives at `https://me-rpg-relay.jbogaardt.workers.dev` (`relayConfig.ts`) and setup is in `relay/README.md`. Changing the API: edit `src/net/relayApi.ts` first, then both sides, and bump `API_VERSION` (the path prefix) if old clients would misbehave: the game and the relay deploy separately, a minute or two apart.
- **Inventory** — `systems/inventory.ts` (Pixi-free, tested): `hero.pack` holds carried items, `BASE_PACK` (10) slots plus the `capacity` of the worn `bag` (sack +4, backpack +8; `packSize`). `equipFromPack`/`unequip`/`dropFromPack`/`dropWorn` either succeed or change nothing and return a reason (the weapon can only be swapped; a bag cannot come off or shrink while the pack needs its room). A one-handed non-bow weapon fits the off-hand too (it adds attack; it has no off-hand art, so `playerOutfit` ignores its look). The `I` key (the `inventory` action; the HUD `I` button on touch) opens the menu on the Inventory tab (`hud/Inventory.ts`: equipped slots, pack grid, tap to pick then Equip / Equip off-hand / Take off / Drop, double click wears or removes; icons are inline SVG in `hud/itemIcons.ts`, since items have no art of their own). The scene attaches `InventoryHandlers` on `enter`. Dropped items are `entities/GroundItem.ts`; the action key picks one up (before swinging). Co-op: guests see a "kept by the host" note, dropping is solo-only (ground items are not in the snapshot), and a friend's chest loot keeps the old wear-if-better rule (`collect(..., stash=false)`). Not saved between visits (the hero never is).
- **Economy: gold, pack and shops** — `Hero` has `gold`; the pack is the Inventory's `hero.pack` (capped, see above), and supplies like potions live in it. Every `Item` has a `value` in gold (`systems/items.ts`); supplies (`potion`, `elixir`) have no slot and a `use` (HP/MP restored) and are drunk with the Inventory screen's Drink button. The shop-side pack moves are at the end of `systems/inventory.ts`: `wearIfBetter` (puts a piece on and sends the old one to the pack), `wearFromPack`, `useFromPack`, `packEntries` (grouped), `isBetter`/`upgrade`. **Money comes mainly from enemies**: each `MobKind` has `gold`, rolled ±30% by `rollGold`; `OverworldScene.hitMob` gives every player the same purse on a kill (like XP) and floats `+Ng`. Chests can also hold gold (`coins`/`purse`/`hoard`). `systems/shops.ts` (Pixi-free, tested): `SHOPS` — four specialists, each with a `keeper` (an `NPC_LOOKS` key), `stock` and a `buys` filter (a shop buys back only its own trade, at `SELL_RATE` 40% of `value`): `smithy` (swords, shields), `armory` (helms, chest, legs), `ranger` (bows, boots, cloak), `apothecary` (potions, elixirs). `buy` wears gear that beats what the hero has, else puts it in the pack, and refuses (taking no gold) when there is no free pack slot. **Chests no longer hold what a shop sells**; they keep the rare pieces (Viking Helm, Legion Armor, Parrying Dagger, elixir) and purses. Keep a piece in one place: stock in one shop, or chests. Maps place a shop with `z.shop(id, col, row)` (`MapData.shops`, checked by `tools/map/check.ts`) and the building with `z.prop('smithy'|...)`. In `OverworldScene` the action key next to a keeper (`CELL * 1.5`) opens a greeting `Dialog` (its `say(lines, onDone)` runs `onDone` after the last line), then `hud/ShopCounter.ts` (`#shop` in `index.html`: Buy/Sell tabs, Wear/Drink buttons) — a modal like the menu: solo it pauses the world, online it only freezes the hero. The shop counter's Sell tab also has Wear/Drink buttons (`ShopCounter.onGearChange` makes the scene redraw the hero). `Hud` shows gold, the Status tab too. **In co-op every player is their own character**: the host keeps each friend's whole `Hero` (stats, gold, pack, gear) and is the only one who changes it. A friend's wishes travel as `do` messages (buy/sell/wear/use + an item code, built by `systems/trader.ts`'s `remoteTrader`; the menu and shop counter talk to a `Trader` and don't know whether it is `localTrader` or remote); the host's `handleTrades`/`tradeFor` check them (known item and shop, the friend within 3 cells of that shop's keeper) and answer with a `pack` message (gold, worn item codes, pack, plus `say` = the reply to show once). `pack` goes to each friend on change and once a second, and `looks` (what every player wears) goes to all, so everyone sees everyone's gear. Item codes are `itemCode`/`itemFromCode` in `systems/inventory.ts` (an item's index in `ITEMS` plus one): adding an item at the end of `ITEMS` is safe, reordering is a protocol change. A guest's Inventory screen stays locked (main's rule), so a guest drinks potions at a shop counter; a friend's character exists only for that game: their solo hero is put back when they leave (`OverworldScene.solo`).
- **Shop buildings** — `public/tilesets/town.png`, built by `tools/map/town.ts` (part of `npm run tilesets`) from the CC0 "Town RPG Pack" by Luis Zuno in `art/town_rpg_pack/` (16px art, doubled to the 32px grid): the pack's inn and tall house are cut out, roofs recoloured, the tall house given the inn's door, and an emblem painted over each door. Coordinates are `BUILDINGS` in `tools/map/catalog.ts`; the prefabs `smithy`, `apothecary` (6x7 cells) and `armory`, `ranger` (3x9) are solid from the ground up. There are no interiors (no map transitions yet): the keeper stands outside the door.
- **Treasure chests** — `systems/chests.ts` (Pixi-free: `CHEST_KINDS` = rows of `public/tilesets/chests.png`, `CHEST_LOOTS`, `collect(hero, loot)`: gear is worn if its slot is empty or it is an upgrade (the old piece goes to the pack), otherwise it goes to the pack, and a full pack leaves the chest shut; potions, XP and gold also work) and `entities/Chest.ts` (open/closed sprite, origin at feet). Zones place them with `z.chest(kind, loot, col, row)` (solid cell; `MapData.chests`, checked by `tools/map/check.ts`). In `OverworldScene` the action key opens a closed chest within `CHEST_REACH` before it swings (`act`); only solo/host decide, and the host sends opened chests to guests as a bitmask (`SnapMsg.chests`, max 30 per map). Guest gear sprites are not synced.
- **Slippery ice**: `systems/ice.ts` (Pixi-free, tested): `isIce` reads the `ice` surface under a player's feet and `stepVelocity` eases `Player.vel` toward the held direction (grip `ICE_ACCEL`) and coasts when keys are released (`ICE_DRAG`); off ice velocity equals the walking velocity, so normal movement is unchanged. Applied to players in `OverworldScene.move` (host/solo; guests only see positions); mobs ignore it. The ice tiles are painted (cracks, glints) by `tools/map/recolor.ts` into the empty corner of `frost_ground.png`; the lake's ring cells keep the snow surface, so only the inner fill is slippery.
- **Ambient life**: `src/entities/ambient.ts` is passive background animation driven by body movement and map metadata (no hooks into collision): footprints that alternate feet and fade within 2-3 s, only on soft terrain (`PRINTS`: `sand`, `snow`, and `puddle` once a puddle ground exists; hero and mobs; pooled, capped at 96), and leaves that drop when the hero moves behind a canopy (a `tree`/`bush`-tagged object drawn over the hero) or swings at one (`Ambient.shake`, called from `OverworldScene.attack`). Leaf colours follow the canopy's sheet (green/frost/dry). It parents everything to `world.layer`. To add an effect, keep it pooled and capped, and key it off `surface`/`tag`/`level` rather than coordinates.
- **`src/map/`** — `types.ts` (`MapData`, `parseMap`) and `MapView.ts`: a render group with a static `ground` layer (its own render group, drawn from a cached instruction list) and a y-sorted `layer` holding map objects (cullable via `CullerPlugin`) plus everything the scene adds (characters, effects). Add entities to `world.layer`, never to the `MapView` itself.
- **`src/assets.ts`** — all loading goes through the Pixi `Assets` manifest: the sprite part manifest plus every part layer used at boot (via `Wardrobe.load`, which registers aliases in the same `Assets` cache) and one bundle per zone (`loadZone(name)`: the map JSON, validated by `parseMap`, then the tilesets it names; `unloadZone`). The map URL carries `__BUILD_ID__` so a deploy never pairs new code with a cached old map. Don't call `Assets.load` ad hoc elsewhere (the `Wardrobe` is the one sanctioned exception, for sprite layers).
- **HTML overlays** (`src/hud/`; markup in `index.html`, styles in `src/ui.css`): `Hud.ts` (HP/MP bars), `Dialog.ts` (`#dialog`; tapping it advances; `layout()` keeps it clear of the touch controls), `Menu.ts` (pause menu: Status / Inventory / Controls / Online, plus Trade while online; the Online tab is `Multiplayer.ts`, which only drives the `Session`) and `MapOverlay.ts` (the co-op map, below) and `Loading.ts` are DOM rather than Pixi so text stays sharp on phones and can use safe-area insets.
- **UI look**: Lamoot's RPG GUI kit (CC-BY 3.0, credited in CREDITS.md). `tools/ui/cut-gui.ts` cuts pieces from `art/rpg_gui_v1/RPG_GUI_v1.png` into `src/ui/` (bundled by Vite via `ui.css`): gold frames used as `border-image` on `.panel` (`.thin` variant), `.wood`/`.paper` backgrounds, plank tabs, square buttons, D-pad arrows. Fonts: Cinzel (titles) and Crimson Text (body) from Fontsource. Reuse these classes for new UI rather than inventing new styles.
- **Touch controls**: `src/core/touch.ts` wires the on-screen D-pad (shown when the primary pointer is a finger or after a touch, hidden again on any physical key press) into `input` as virtual arrow-key presses (`input.setVirtual`), and makes every `[data-key]` element (A = KeyJ, B = KeyK, the ☰ and menu ✕ = Escape) press that key while held, so game code only ever reads key codes. To add a button, add a `data-key` element.
- **Map pipeline** — maps are built by agents from code, not painted: **use the `build-zone` skill** (`.claude/skills/build-zone/SKILL.md`) for any map change.
  - `maps/<zone>.ts` (source of truth) uses the `Zone` builder (`tools/map/zone.ts`: `fill`, `patch`, `forest`, `prop`, `stamp`, `plateau`, `block`/`unblock`, `spawn`/`npc`/`mob`) with named assets from `tools/map/catalog.ts`. `npm run map -- build` compiles it to `public/maps/<zone>.json`, renders `maps/out/<zone>.png` + `.debug.png` (gitignored), and runs `tools/map/check.ts`. Never hand-edit the JSON; `npm run build` fails if it's stale or a check errors.
  - The JSON is `MapData` v2 (`src/map/types.ts`): 32px ground cells referencing 32x32 regions of tileset sheets, free-placed objects (y-sorted by bottom edge, or by an explicit `z` for flat art like cliffs; each can carry a `tag` such as tree/bush/rock/cliff), a collision cell list, per-cell terrain metadata (`surface` names like grass/sand/snow, `level` height, `ramps` = stairs) for game systems, spawn/NPC cells and mob spawns. The game reads collision, surface (footprints) and tags (leaf fall); `level`/`ramps` are for height-aware movement (see Roadmap). `MapView` renders it in the game; `tools/map/image.ts` renders the same way in Node for previews. Tilesets live in `public/tilesets/`; all art is cut on the 32px grid.
  - **Cliffs**: `z.plateau(rect, {kind, stairs})` builds a raised plateau from the Avalon blob on `Cliff_tileset.png` (cut along its grass hole so it scales to any size >= 4x4; measurements in `CLIFF`, `tools/map/catalog.ts`). `rect` is the walkable top; the rim ring and two face rows around it block; stairs are the only way up and become `ramps`. `kind` picks `grass`/`frost`/`dry` (`frost_cliffs.png`, `dry_cliffs.png`, derived in `recolor.ts`). The art is flat ground-level (`z` below all entities), so the hero draws over it. `check.ts` fails if two open cells of different level touch without stairs (a gap in a rim). `Extra_Unfinished4.png` (stone wall, door, brown drop-off) and `graphics-tiles-waterflow.png` (animated water) are still uncatalogued.
  - Collision for props is derived from their art (cells covered by the bottom `solid.band` px of the sprite), forests block their rect, so collision tracks the visuals. The tilesets have no foliage edge tiles — all vegetation is prefabs, and canopies on `object-layer.png` must be split into bleed-free parts (see `treeA`).
  - **Biomes**: the pack only has grass/sand/water/stone, so snow, ice, frosted trees and withered trees are *derived* sheets (`frost_ground.png`, `frost_objects.png`, `dry_objects.png`, `ground_plus.png`) generated by `tools/map/recolor.ts` (`npm run tilesets`, outputs committed). Same coordinates as the originals, so catalog entries just point at another sheet. `maps/overworld.ts` is one 96x72 world: Frostlands (north), Greenwood (south-west, spawn), Scorched Waste (south-east). Snow and sand both blend into grass, so biomes are kept apart by grass bands.

## Conventions

- **Keep multiplayer in sync with single player.** Co-op is not an afterthought: whenever a feature touches gameplay state (stats, gold, pack, gear, shops, chests, combat, mobs, map objects, a new key or menu tab), decide how it behaves for the host and for a guest *in the same change*. The host owns every hero and all simulation; a guest only sends wishes (`do`, `tr`, input) and renders what it is told (`snap`, `pack`, `looks`, `trade`). If something is solo/host-only for now, say so in the UI (e.g. the guest's "kept by the host" note) and in this file. Anything new that a guest must see goes through `src/net/protocol.ts` (validated in `parseMessage`, version bumped, a `protocol.test.ts` case) and `session.ts`; anything new that needs a guest's input is a numbered/ackable command, not a raw event. Add unit tests for the pure rules and an `e2e/multiplayer.spec.ts` case when a flow spans two players. **When you change a single-player system, update the co-op bullets above (and the matching ones in the other direction) so this file always describes both.**

- TypeScript is strict plus `noUncheckedIndexedAccess` and `verbatimModuleSyntax` for game code (`tools/` indexes freely). Prefer a clear error over `!` when data can be missing; `!` is fine for DOM lookups that `index.html` guarantees.
- Prettier owns formatting (single quotes, width 120); ESLint is type-aware and bans floating promises.
- New rules/maths go in a Pixi-free module with a `*.test.ts` beside it.

## Deployment

The relay (`relay/`) deploys separately: Cloudflare builds and deploys it from `main` itself (no GitHub workflow); see `relay/README.md`. A relay change only reaches players once that build has finished, so wait for it before relying on a new API.

`.github/workflows/deploy.yml` builds and publishes `dist/` to GitHub Pages on every push to `main` (repo Settings → Pages → Source must be "GitHub Actions"). `vite.config.ts` sets `base: './'` so asset URLs work under the `/<repo>/` subpath — keep asset references relative (put static files in `public/` and don't use root-absolute `/...` paths).
