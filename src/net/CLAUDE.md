# src/net (co-op)

Also read `docs/dungeon-master.md` for what the host being the DM means. Detail moved out of the root `CLAUDE.md` (which has the layers, commands, procedure and conventions); words such as "above" or "below" inside these bullets refer to this file or the map in the root. Keep the bullet for a feature up to date in the same change.

- **Co-op (a Dungeon Master and up to 3 players, peer-to-peer gameplay)** — `src/net/`. Settings → **Online** tab: **Host → Create Game** shows a short code like `mighty-apples` (also a `#join=` link) and a roster of the four seats; up to three friends **Join** with the code; the host taps **Start Game** (or the last seat fills) and the code stops working. `PeerLink.ts` is one `RTCPeerConnection` + data channel, one per friend (a star: every friend connects to the host, never to each other) (`{ ordered: false, maxRetransmits: 0 }`, public STUN only, so no TURN for gameplay: two strict NATs can't connect). An offer/answer is a full session description with every ICE candidate (gathering waits for `complete`, capped at 10 s), deflated by `CompressionStream` and base64url-encoded (`signal.ts`). **Setting up a game goes through the matchmaking relay** (`relay/`, a Cloudflare Worker). An offer fits exactly one connection, so the host prepares one offer per seat up front and `relayClient.ts` stores them under the code; each friend who types the code is given the next free seat and its offer, answers it, and the host long-polls for answers (cursor-based), so each exchange takes about a second; `roomCode.ts` (shared with the Worker) is the two-word code format; `relayApi.ts` is the wire format; `relayConfig.ts` holds the deployed relay's URL (`DEPLOYED_RELAY_URL`, or `VITE_RELAY_URL` at build time; empty means online play is shown as not set up). **The lobby and joining, with no addresses to type** (`hud/Multiplayer.ts`, `net/hostPlan.ts`, `content/campaignChoice.ts` `HOST_STORIES`/`worldFor`/`queryForTag`): before Create Game the host picks a **Story** (This world, A new story told as you go = a live world, The Vale, Emberfall Isle) and how hard the world pushes (`Session.hostPressure`, starting `Arena.pressure`); a story the page does not already play is a different world, which the page plays from its address, so the page moves there itself (`location.assign` with `queryForTag`), the choices ride across the reload in sessionStorage (`saveHostPlan`/`takeHostPlan`, read once) and the new page creates the game at once (`Session.autoCreate`, `OverworldScene.enter`). A friend only types the two-word code: the host's hello carries its world after a `#` (`setContentTag`), and a friend whose page plays another world closes the link, moves its page to the host's world and joins the same code again (`Session.worldMismatch`, set in `main.ts`, goes to `?campaign=...#join=<code>&go=1`; `Session.autoJoin` makes the scene join without another tap); the host gives such a friend `WORLD_GRACE_MS` 6 s to move before it drops the link, then a seat is refilled as usual. A friend whose page cannot move is turned away with a message. The old join link (`Copy Join Link`) still works. Gameplay never goes through the relay. `session.ts` is the state shared by the menu and the game loop (`mode`, `status`, `role`, `slot`, `connectedSlots()`, `roster()`, the host's `code`/`lobbyOpen`, parked incoming messages, version handshake) and runs `createGame()` / `joinGame()` / `startGame()`: the host keeps a `Seat` per friend (waiting, joining, connected), refills a seat with a fresh offer when its friend leaves while the code is open, ends the game when the last friend leaves after Start, and a friend's drop never affects the others; the host leaving ends it for everyone (no host migration). `looks.ts` gives each player number its own clothes, ring colour and name; the scene tags everyone "P1"–"P4" in co-op. `protocol.ts` defines the messages and validates everything from the peer (`parseMessage` never throws); `mobWire.ts` flattens a `MobView` (systems/combat.ts) to the tuple a snapshot carries and back (a mob exposes a plain `MobView`; the wire format is net's: `net/` imports only `core/` and `systems/`, and `entities/` never imports `net/`); `interp.ts` glides snapshots. Roles: **host** (the Dungeon Master, above) runs the normal simulation plus a `Player` per friend driven by that friend's input (`reconcileGuests` keeps them in step with the session's connected seats), and sends each friend a snapshot at 25 Hz (the players in that friend's zone, that friend's own stats, the items on the ground (listed when they change and once a second; absent means unchanged), the mobs *near that friend* (`net/feed.ts`, `MobFeed`, one per friend and zone: within the view radius the friend reports in its input message (`vr`) plus a margin; a mob whose state has not changed is repeated only every 0.24 s, and its timer is 0 outside windup/recover/dead so a still mob really is unchanged) and the one-shot events near that friend (`eventInView`: the view radius plus the margin, plus how far a shot can fly) that they have not acknowledged, as flat tuples (`EventWire`, `encodeEvent`/`decodeEvent`, about 25 B each) and only as many as fit the room the rest leaves under `SNAP_BUDGET` (1100 characters, `fitEvents`, newest first); about 0.2 KB quiet and under 1.2 KB in a big fight with four players: a message over about 1.2 KB is split in transit and, on this lossy channel, losing any piece loses all of it, so keep it small; `protocol.test.ts` checks a busy snapshot with a full ground list); the guest merges two snapshots that arrive in one frame (`mergeSnapshots`: a snapshot leaves out unchanged mobs and ground, so the older one's still count); **client** runs no simulation: it sends held keys at 30 Hz and renders snapshots (`Mob.setRemote`/`updateRemote`), with no prediction. The channel is lossy, so inputs are *state* (keys held) plus running counters for presses, and one-shot visuals (damage numbers, slashes, bolts; an enemy's shot is a `bolt` event with a `color`, drawn but never simulated on the guest) ride in snapshots with ids and are shown once; the guest's input messages carry the newest id it has shown (`ack`), so the host stops repeating an event once it has arrived (it still expires after 0.6 s if no ack comes). Events caused by a player carry that player's number (`p`) so the guest plays the pose on the right character. Online play never pauses the world (menu and dialogs are local overlays); kills share XP between every player of the party (never the DM); a friend's solo hero is restored when they leave, and the game returns to solo when nobody is connected. - **Player trading (co-op)** — `systems/trade.ts` (Pixi-free, tested): the host's `TradeBook` is the only authority. Players (the host included) send `TradeCommand`s (`ask`, `yes`/`no`, `offer` = item codes + gold, `ready` on/off, `cancel`); the book checks them against the real heroes. Flow: a player asks someone within `TRADE_START` (3 cells) from the **Trade tab** of the menu (shown only online, `Menu.setOnline`; each player is listed with a button that is disabled when too far); the other gets an Accept/Deny prompt (`#trade-request`; lapses after 30 s; two players asking each other counts as yes); then the shared window (`#trade`, `hud/Trade.ts`, a modal like the shop counter that freezes the hero) where each side offers pack items and gold; **any change to either offer clears both Accept marks**, and when both accept the swap happens atomically or not at all (goods and pack room are re-checked; a failure changes nothing and says why). The trade ends if players drift past `TRADE_KEEP` (5 cells), leave, or either cancels (Esc / the ✕ cancels an open trade). Only pack items can be offered (not worn gear). On the wire (`tr` guest→host, `trade` host→guest, `protocol.ts`) commands are numbered and the guest repeats every unacknowledged one until the host's `ack` covers it (the host takes only the next number), so the lossy channel can't drop a click; the host sends each friend their view/note when it changes and once a second; the gold/pack result then arrives through the normal `pack` message. `TradeUi.sync` draws from a `TradeView` every frame; `OverworldScene` (`syncTrade`, `tradeCommand`, `handleTradeSteps`, `sendTrade`) joins it to the book (host: direct; guest: queue + host view). The UI keeps a local draft of your offer while commands are unacknowledged.
